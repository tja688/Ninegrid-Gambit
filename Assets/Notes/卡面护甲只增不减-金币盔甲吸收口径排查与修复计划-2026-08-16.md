# 卡面护甲“只增不减”复盘：金币盔甲吸收口径，不是丢指令

> 日期：2026-08-16
> 性质：过程笔记（非权威）。代码不变量以 `docs/adr/0005-card-face-beat-commit.md`、`docs/adr/0028-damage-formula-armor-and-reduction.md`、`docs/adr/0045-unified-card-face-stat-projection.md` 为准。
> 结论先行：测试者这局里“玩家卡面护甲只增不减”的断点**不在卡面数值链路**，而在**金币盔甲（`relic.gold_armor`）的吸收口径**：真实当前护甲本来就没有减少（金币代偿），但伤害飘字仍把“被金币抵消的甲伤”当作普通护甲伤害显示。卡面不动是对的，飘字/日志口径在骗人。
> 同时发现一个会放大误判的日志口径问题：`BattleTraceRecorder.TryCaptureCard` 的快照甲写的是**有效护甲**，不是卡面/结算事件使用的**当前护甲**。

## 2. 代码根因

### 2.1 核心：`DealDamageAction` 的甲伤拆分口径

`Assets/Scripts/NineGrid.Foundation/NineGrid.Core/Domain/Actions/CoreActions.cs`：

- L122：`armorDamage = Math.Min(armor, damage)` —— **金币代偿前**的毛甲伤。
- L124–127：Avatar 有 `GoldArmorAbsorb` 时，`goldAbsorbed` 吃掉一部分甲伤。
- L129：`armorLoss = armorDamage - goldAbsorbed` —— 真正会让当前甲下降的部分。
- L135：当前甲只减 `armorLoss`。
- L151：只有 `armorLoss > 0` 才发 `ArmorChanged`。所以全代偿时卡面没有扣甲指令，这是正确的。
- L173–180：`DamageDealt` 调 `WithDamageSplit(armorDamage, hpLoss)`，把**代偿前毛甲伤**交给表现层。

`CoreGameEvent.cs` L46 的注释也写明：`ArmorDamage` “含金甲代偿部分”。内容侧 `effect_templates.json` 的 `tpl.relic.gold_armor.rule` 设计文本也是“每5金币抵消1点当前护甲伤害”——即被代偿的甲伤**不应该**表现为当前甲下降。因此 `DamageDealt` 的甲伤字段是“毛甲伤”，而卡面跟随的是“净甲伤/当前甲”。两个口径有意或无意地分叉了。

### 2.2 表现：飘字消费了毛甲伤

`Assets/Scripts/NineGrid.Presentation/Flow/Presentation/DamageFloaterBeatHandler.cs` L70–83：

- `ShowDamage` 拆分模式下，`armorDamage = Math.Max(0, gameEvent.ArmorDamage)`。
- `armorDamage > 0` 就 `RequestSpawnArmorDamage`（绿灰色“甲伤”飘字）。
- 于是金币全代偿的命中（op 261/263）仍会飘“甲伤 4”，但卡面甲确实是 4 不动。测试者自然读成“卡面漏扣”。

同样的问题也出现在人读战斗日志：`BattleLogRecorder.BuildDamage` L476–506 会把 `e.ArmorDamage` 直接写成“甲 N”（L489–491），金币代偿部分仍被读作“本次掉了 N 甲”。所以无论看飘字还是看游戏内战斗日志，都会得到“甲被扣了但卡面不动”的错觉。

### 2.3 金币消费反馈太弱

`GoldGainBeatHandler` 对 `GoldModified(message=goldArmor, delta=-20)` 会发 `GoldGainPresentationRequested`；但 `GoldGainPresentationBinder.OnGoldGainPresentationRequested` 的 spend 分支只做：

- 播放消费音效；
- `PlayerInfoHud.SnapGold`；
- `FlowTrace.GoldSpent`。

没有从受击卡位置飘出“金币 -20”或金币代偿视觉，因此玩家视觉锚点仍留在绿色甲伤飘字上。

### 2.4 次生：BattleTrace 快照的甲也是另一个口径

`Assets/Scripts/NineGrid.Presentation/Flow/Diagnostics/BattleTraceRecorder.cs` L208–232：

- `TryCaptureCard` 的 `armor` 取 `stats.GetEffectiveInt(card, StatId.Armor)` —— **有效护甲**。
- 卡面甲与结算事件 `RemainingArmor` 是**当前护甲**。

这解释了日志里 op 261 目标快照 `armor=3`、事件 `remainingArmor=4` 的分叉（有效甲 3 + 借甲图腾 1 = 当前甲 4）。它不是本次卡面 bug 的根因，但会让“用日志对卡面”的人持续误判。

## 3. 为什么不是老链路断点

对照 `Assets/Notes/卡面数值显示链路-认知模型-2026-08-10.md` 的候选：

- **A（改值不发事件）**：`ResetCurrentArmorAction` 现在已发 `ArmorChanged`，且 `PhaseSystem.StartNode` 已把 reset 放在 `FillEmptySlots` 之前（`PhaseActions.cs` L68–96、`PhaseSystem.cs` L176–178）。本次也不涉及静默扣甲。
- **B（认领即丢）**：`CardFaceStatHandler.ApplyArmor` 现在有 `LogResolveMiss/LogViewMiss`；ConsoleLog 无对应 Warning。
- **C（批次吞没）**：`BattleBeatScheduler` 已有 `DiagnoseDiscardedPending` 和 `DiagnoseUnconsumed`；ConsoleLog 无对应 Error。
- **D/E（节点解析/模板初值）**：加甲能显示、拿遗物前扣甲也能显示，节点解析不是本局变量。

所以本局不是“卡面数值管线断链”，而是**数值语义与演出口径不一致**。

## 4. 解决方案 Plan

### P0-1 Core：把“金币代偿甲伤”显式带进事件（最小侵入）

在 `CoreGameEvent` 增加只读字段：

```csharp
/// <summary>仅 DamageDealt：由金币盔甲等代偿的护甲伤害量（含在 ArmorDamage 内）。</summary>
public int GoldAbsorbedArmor { get; private set; }

public CoreGameEvent WithGoldAbsorbedArmor(int amount)
{
    GoldAbsorbedArmor = Math.Max(0, amount);
    return this;
}
```

`DealDamageAction` 的 `DamageDealt` 事件追加：

```csharp
.WithDamageSplit(armorDamage, hpLoss)
.WithGoldAbsorbedArmor(goldAbsorbed)
```

保持 `ArmorDamage` = 毛甲伤不变，避免破坏现有受击反馈、屏幕震动和既有日志读者；新增字段只做拆账。同步补 `IgnoreArmor` 路径为 0。

### P0-2 表现：飘字按“净甲伤 + 金币代偿”拆账

`DamageFloaterBeatHandler` 拆分模式改为：

```csharp
var goldAbsorbed = Math.Max(0, gameEvent.GoldAbsorbedArmor);
var netArmorDamage = Math.Max(0, gameEvent.ArmorDamage - goldAbsorbed);
if (netArmorDamage > 0)
{
    DamageNumberHook.RequestSpawnArmorDamage(pos.Value, netArmorDamage);
}

if (goldAbsorbed > 0)
{
    DamageNumberHook.RequestSpawnGoldArmorSpend(
        pos.Value,
        goldAbsorbed * GoldArmorAbsorbGoldPerArmor); // 或直接显示代偿甲伤点数
}
```

产品二选一（建议先在 Notes 定口径，再改）：

- **方案 A（推荐）**：受击位置飘“金币 -N”（`N = goldAbsorbed * 5`，金币色），不再飘被代偿部分的甲伤。真实甲伤仍有绿灰色飘字。
- **方案 B**：只抑制被代偿部分的甲伤飘字，金币消费继续只走 HUD；改动最小，但受击位置反馈略弱。

无论 A/B，`ApplyHitFeedback` 仍可使用毛甲伤 `ArmorDamage` 维持打击感，不要顺手改成净甲伤。

同批修改 `BattleLogRecorder.BuildDamage`：当 `GoldAbsorbedArmor > 0` 时，把详情从“甲 4”改成“甲 0 · 金币代偿 4”（或“甲净 0 / 金币 -20”），与卡面当前甲口径一致。

### P0-3 金币消费视觉补强

`GoldGainPresentationBinder` 的 spend 分支对 `reason == "goldArmor"` 且 `OriginWorld.HasValue` 时，增加一条从受击卡到金币 HUD 的短途金币飞损/脉冲；不占用主线 ack，失败按既有金币表现策略降级。

### P1 日志口径对齐

- `BattleTraceRecorder.TryCaptureCard`：把 `armor` 改为 `StatArmorUtility.GetCurrentArmor(card)`（与卡面/`RemainingArmor` 同口径）；若外部还想读有效甲，给 `BattleTraceCardSnap` 增加 `effectiveArmor` 字段，不要继续复用 `armor`。
- `BattleTraceEventRow` 建议增加 `armorDamage / hpDamage / goldAbsorbedArmor` 三个字段，否则以后排查“金币代偿 vs 真实甲伤”仍要回源码。
- 同步更新 `.cursor/skills/table-nine-battlelog-analysis/SKILL.md`：说明 op 快照甲 = 当前甲，事件 `remainingArmor` 才是该拍结算后当前甲。

### P2 回归护栏

Core：

1. 金币盔甲全代偿：当前甲不变、无 `ArmorChanged`、`GoldModified delta=-5*k`、`DamageDealt.GoldAbsorbedArmor==k`、`HpDamage` 只含溢出。
2. 部分代偿：`armorLoss = armorDamage - k`，`ArmorChanged` 携带 `RemainingArmor` 正确，`GoldAbsorbedArmor==k`。
3. 无金币/无遗物：`GoldAbsorbedArmor==0`，行为与旧版一致。
4. 账本重放：`CardFaceLedgerModel` 重放这些事件后，Avatar 甲仍等于 oracle 当前甲。

表现：

5. `DamageFloaterBeatHandler` 对“全代偿”不产 `ArmorDamage` 飘字，产金币代偿飘字/请求。
6. 对“部分代偿”同时产净甲伤与金币代偿两个数字。
7. BattleTrace 快照与同 op 首条 `HpChanged/ArmorChanged` 的 `remainingArmor` 可比性回归。
8. `BattleLogRecorder.BuildDamage` 在金币代偿时不再把代偿部分计为“甲 N”，文案与卡面当前甲一致。

### P3 文档

- 本复盘落地后，修订 `Assets/Notes/卡面数值显示链路-认知模型-2026-08-10.md` 的候选断点状态：A/B/C 已被当前源码修复或加诊断；新增“金币代偿毛/净甲伤”为一个语义断点。
- 若决定把 `ArmorDamage` 从毛口径改为净口径，先单独 ADR；本 Plan 默认**不改既有 `ArmorDamage` 语义**，只加 `GoldAbsorbedArmor`。

## 5. 验收标准

1. 复现测试者局（同 seed）到拿金币盔甲后：满金时被怪打，卡面甲不动、受击位置不再出现绿灰色“甲伤 N”，而是出现金币代偿反馈；金币 HUD 扣款正确。
2. 金币不足时：只代偿可支付部分，卡面甲按净损失下降，绿灰甲伤飘字只显示净损失。
3. 无金币盔甲时：甲伤飘字、卡面甲、BattleTrace 快照与事件与旧版表现一致。
4. 四轨日志中能直接读出：`ArmorDamage`（毛）、`GoldAbsorbedArmor`、`RemainingArmor`（净），无需再人工回源码拆账。

---

## 6. 风险与不做的事

- **不要把卡面甲强行扣掉金币代偿部分**：那会让卡面显示值背离 Core 当前甲，重新制造真正的“卡面 vs 真实数值”漂移。
- 不要为了本问题引入“卡面回头读 Core 对账”；继续维持 ADR-0005 的单向指令链。
- 若策划希望金币盔甲“看起来像扣甲”，应通过视觉（金盾闪烁/金币碎裂）表达，而不是改当前甲数值。
