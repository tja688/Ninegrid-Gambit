你的这个问题，我建议不要把它当成“攻击 Flow 和反击 Flow 怎么排队”，而是把它提升成一个表现层语义：

**一次玩家攻击敌人的交互，本质是一个 CombatExchange，小战斗交换。**

在这个 `CombatExchange` 里，允许内部有多个 Strike：

```text
CombatExchange
├─ Strike 1：玩家 → 敌人
│  ├─ 攻击表现
│  ├─ Impact
│  ├─ 敌人受击 / 扣血 / 死亡
│  └─ StrikeEnd
├─ Strike 2：敌人 → 玩家  // 只有敌人还活着才存在
│  ├─ 反击表现
│  ├─ Impact
│  ├─ 玩家受击 / 扣血 / 死亡
│  └─ StrikeEnd
└─ CombatExchangeEnd
```

你现在并行严重，大概率是因为表现层在做：

```text
Evt_DamageDealt → CardAttackFlow
Evt_DamageDealt → CounterattackFlow
Evt_MonsterKilled → CardKillFlow
Evt_BoardRotated → BoardRotateFlow
```

然后 `PerformancePlanBuilder` 按事件或 `ActionId` 粗暴拆成多个 Flow，导致“死亡”“反击”“受击”互相不知道谁属于谁，于是并行、抢 Actor、抢 HP 动画、抢消失动画。

更优雅的方案是：

## 1. 内核继续串行，但给事件打上 CombatScope / StrikeId

不要让表现层靠猜。

内核事件仍然是事实，不直接说“怎么演”，但每条战斗相关事件要带因果上下文：

```csharp
public struct CombatContext
{
    public CombatId combatId;
    public StrikeId strikeId;
    public StrikeRole role; // PrimaryAttack / CounterAttack
    public int beatIndex;   // 0 玩家攻击，1 敌人反击
}
```

例如：

```csharp
Evt_CombatExchangeBegin(combatId, attackerUid, defenderUid)

Evt_StrikeBegin(combatId, strikeId, role: PrimaryAttack, sourceUid: player, targetUid: enemy)

Evt_DamageDealt(
    combatId,
    strikeId,
    sourceUid: player,
    targetUid: enemy,
    amount,
    hpBefore,
    hpAfter,
    armorBefore,
    armorAfter,
    isFatal
)

Evt_CardKilled(
    combatId,
    strikeId,
    killedUid: enemy,
    killerUid: player
)

Evt_CardRemoved(
    combatId,
    strikeId,
    uid: enemy,
    fromSlot
)

Evt_StrikeEnd(combatId, strikeId)

Evt_StrikeBegin(combatId, strikeId2, role: CounterAttack, sourceUid: enemy, targetUid: player)

Evt_DamageDealt(... targetUid: player ...)

Evt_PlayerKilled(...)

Evt_StrikeEnd(...)

Evt_CombatExchangeEnd(combatId)
```

重点不是事件名字，而是这两个字段：

```text
combatId：这批事件属于同一次小战斗
strikeId：这条伤害 / 死亡 / 移除属于哪一次出手
```

这样表现层就不会把“敌人死亡”和“敌人反击”当成两个可以同时播的独立 Flow。

## 2. 表现层不要 1 Event = 1 Flow，而是“折叠事件段”为 StrikeFlow

你现在已经有 `CardAttackFlow`、`CounterattackFlow`、`CounterattackKillFlow`、`CardKillFlow`，但我建议收敛成一个更统一的东西：

```text
StrikeFlow
```

它的 payload 是表现层从 EventLog 里折叠出来的结果：

```csharp
public class StrikeFlowPayload
{
    public CombatId combatId;
    public StrikeId strikeId;

    public int sourceUid;
    public int targetUid;

    public StrikeRole role; 
    // PrimaryAttack / CounterAttack

    public DamageViewDelta damageDelta;

    public bool targetKilled;
    public bool targetRemoved;
    public SlotId? removedFromSlot;

    public bool isPlayerDeath;
}
```

然后三种情况自然变成：

### 情况一：敌人没死，玩家也没死

```text
CombatExchangePlan
├─ StrikeFlow(PlayerAttack, targetKilled=false)
├─ StrikeFlow(CounterAttack, targetKilled=false)
└─ PostCombatFlow(BoardRotate / Fill / etc.)
```

表现顺序就是：

```text
玩家攻击敌人
→ 敌人受击
→ 敌人反击玩家
→ 玩家受击
→ 场地后续
```

### 情况二：敌人被打死

```text
CombatExchangePlan
├─ StrikeFlow(PlayerAttack, targetKilled=true, targetRemoved=true)
└─ PostCombatFlow(Fill / BoardRotate / etc.)
```

表现顺序就是：

```text
玩家攻击敌人
→ 敌人受击
→ 敌人死亡 / 移除
→ 场地后续
```

核心点：**不要生成 CounterAttackFlow，或者即使 TryCounterAttackAction 存在，也应该因为敌人已死亡而不产生 StrikeBegin。**

### 情况三：玩家被反击打死

```text
CombatExchangePlan
├─ StrikeFlow(PlayerAttack, targetKilled=false)
├─ StrikeFlow(CounterAttack, targetKilled=true, isPlayerDeath=true)
└─ DefeatFlow / 或者你规则允许的话再接 BoardRotate
```

表现顺序就是：

```text
玩家攻击敌人
→ 敌人受击
→ 敌人反击玩家
→ 玩家死亡
→ 后续阶段
```

## 3. 把“反击”做成 TryCounterStrikeAction，而不是表现层自己判断

内核里可以这样组织：

```csharp
BattleAction
```

只是一个宏动作，它不直接改血，而是建立战斗上下文并压入子动作：

```csharp
BattleAction.Resolve()
{
    var combatId = NewCombatId();

    Emit(new Evt_CombatExchangeBegin(combatId, playerUid, enemyUid));

    // 注意如果你的 Pipeline 是栈，压入顺序要反过来
    Push(new CombatExchangeEndAction(combatId));
    Push(new TryCounterStrikeAction(combatId, enemyUid, playerUid));
    Push(new StrikeAction(combatId, playerUid, enemyUid, StrikeRole.PrimaryAttack));
}
```

`StrikeAction` 再拆：

```csharp
StrikeAction.Resolve()
{
    var strikeId = NewStrikeId();

    Emit(new Evt_StrikeBegin(combatId, strikeId, role, sourceUid, targetUid));

    Push(new StrikeEndAction(combatId, strikeId));
    Push(new DealDamageAction(sourceUid, targetUid, strikeId, combatId));
}
```

`DealDamageAction` 扣血后如果致死，继续按你原来的流水线压：

```text
DealDamageAction
→ KillAction
→ RemoveCardAction
```

但这些 Action 都继承同一个：

```text
combatId
strikeId
causeActionId
```

这样敌人被玩家这一击打死时：

```text
StrikeAction(player → enemy)
→ DealDamageAction
→ KillAction(enemy)
→ RemoveCardAction(enemy)
→ StrikeEnd
→ TryCounterStrikeAction
```

`TryCounterStrikeAction` 执行时一查：

```csharp
if (!enemy.IsAlive || !enemy.IsOnBoard)
    return;
```

于是不会产生反击事件。

这个模型很干净，因为“敌人死了不能反击”是内核事实，不是表现层猜出来的。

## 4. 表现层 Builder 要加一个硬规则：CombatScope 内禁止跨 Strike 并行

你的 `PerformancePlanBuilder` 可以这样做：

```text
Batch
→ 按 combatId 找到 CombatExchange 段
→ 段内按 strikeId / beatIndex 折叠成 StrikeFlow
→ StrikeFlow 之间串行
→ StrikeFlow 内部允许并行
→ CombatExchangeEnd 之后才允许 BoardRotate / Fill / Reward / Defeat 等后续 Flow
```

换句话说：

```text
CombatExchange 是大栅栏
Strike 是小栅栏
Impact 是 Strike 内部同步点
```

建议规则：

```text
不同 CombatExchange：一般不会同批并行，除非你未来有多单位同时战斗机制
同一个 CombatExchange 内：Strike 串行
同一个 Strike 内：攻击动作、特效、音效可并行；Impact 后 HP / HitFlash / Death 串行或局部并行
CombatExchangeEnd 后：才接补牌、旋转、结算、通关检查
```

这会立刻解决你说的“并行比较严重”。

## 5. Death / Kill 不要作为顶层独立 CardKillFlow 抢跑

这是很关键的小点。

如果死亡是某次攻击造成的，那么死亡表现应该挂在那次 `StrikeFlow` 里面，而不是独立排一个 `CardKillFlow`。

也就是说，不要这样：

```text
CardAttackFlow
CardKillFlow
CounterattackFlow
BoardRotateFlow
```

而是这样：

```text
StrikeFlow(PlayerAttack)
{
    AttackMotion
    Impact
    DamageNumber / HpBar
    if targetKilled:
        DeathAnim
        RemoveActor
}

StrikeFlow(CounterAttack)
{
    AttackMotion
    Impact
    DamageNumber / HpBar
    if targetKilled:
        PlayerDeathAnim
}
```

`CardKillFlow` 只保留给“非攻击造成的死亡”，例如毒、陷阱、遗物弹射、场地效果等。
但即便是这些，也最好依然折叠到某个 `causeActionId` 或 `effectScopeId` 下，而不是裸奔。

## 6. HP / 护甲表现不要直接吃 BindableProperty 即时变化

你文档里有“批末 Snapshot 对齐”的设计，这里正好用上。

因为内核是单帧跑完的，模型里的 HP 会立刻变成最终值。如果战斗 View 直接监听 `BindableProperty<int> hp`，就会出现：

```text
动画还没打到
HP 条已经变了
死亡动画和反击动画又开始抢
```

所以战斗中的 HP / 护甲建议采用：

```text
Flow Impact 驱动显示变化
批末 ReconcileFromSnapshot 兜底校准
```

也就是：

```text
Core Model：立即变，权威
Battle View：不直接即时响应战斗 HP 变化
StrikeFlow Impact：播放扣血、护甲破裂、死亡
BatchEnd Snapshot：最终对齐
```

HUD 金币、互动次数这些可以直连；但战斗 HP / 护甲 / 死亡生命周期不要直连，必须走 Flow。

## 7. 我建议你最终落成这个结构

### Core Event 层

最小新增这些语义事件：

```csharp
Evt_CombatExchangeBegin
Evt_StrikeBegin
Evt_StrikeEnd
Evt_CombatExchangeEnd
```

原有事件保留：

```csharp
Evt_DamageDealt
Evt_HpChanged
Evt_ArmorChanged
Evt_CardKilled
Evt_CardRemoved
Evt_PlayerKilled
Evt_CardMoved
Evt_BoardRotated
```

但战斗相关事件都补：

```csharp
combatId
strikeId
causeActionId
seq
```

### Presentation Plan 层

新增：

```csharp
CombatExchangePlanBuilder
```

它负责把事件折叠成：

```csharp
CombatExchangeStep
├─ StrikeStep(PlayerAttack)
├─ StrikeStep(CounterAttack)?
└─ PostCombatStep?
```

### Flow 层

把现有几个 Flow 收敛：

```text
CardAttackFlow          → StrikeFlow(role = PrimaryAttack)
CounterattackFlow       → StrikeFlow(role = CounterAttack)
CounterattackKillFlow   → StrikeFlow(role = CounterAttack, targetKilled = true)
CardKillFlow            → StrikeFlow 内部 DeathPart，或仅保留给非 Strike 死亡
```

最后表现层播放就变成：

```csharp
await PlayStrike(playerAttackStep);

if (counterAttackStep != null)
    await PlayStrike(counterAttackStep);

await PlayPostCombatSteps();
await ReconcileFromSnapshot();
SendPresentationFinished();
```

## 8. 这套方案的核心原则

你这个场景最优雅的解法不是“加更多 await”或者“强行延迟反击”，而是：

```text
内核负责因果：
谁打谁、谁死了、还能不能反击。

EventLog 负责标注：
这些事件属于同一次 CombatExchange，属于哪一次 Strike。

表现层负责折叠：
不要一个事件一个 Flow，而是一段事件折叠成一个 StrikeFlow。

播放器负责边界：
Strike 之间串行，Strike 内部局部并行，批末 Snapshot 对齐。
```

一句话总结：

**把“玩家攻击—敌人受击—敌人反击—玩家受击/死亡”建模成一个 CombatExchange，而不是几个互相独立的表现 Flow。死亡、移除、扣血都挂到造成它的 Strike 上，反击由内核的 TryCounterStrikeAction 决定是否生成。**

这样你这三条期望顺序会自然成立，而且后面接补牌、场地卡转动、通关检查也会很顺。
