# 层级系统承载能力评估（内核 + 表现层）

## 结论（先看）

当前实现整体方向没有走偏，核心架构具备承载原层级系统设计的能力：

- Core 侧已经形成可用的节点相位流水线（`GamePhase` + `PhaseSystem`）。
- Content 侧已经把节点配额、房间类型、击杀奖励做成可配置规则（`NodeDeckRule`、`RewardPool`、`RoomDefinition`）。
- Presentation 侧已经接通了 Command/Event 驱动与主流程屏切换（`ShellCommandRouter` + `GamePhaseFlowShellProjection`）。

但存在几个会直接影响设计一致性的关键缺口，尤其是跨节点玩家构筑持久化和生产桥接参数传递，这些点不补会出现“架构看起来对，但实际跑偏”的情况。

---

## 一、与原设计对齐良好的部分

## 1) 宏观结构与节点流转

- 设计目标：3 层 x 9 节点，共 27 关。
- 现状：`RunModel` 中 `FinalFloor=3`，`NodesPerFloor=9`，`AdvanceNode` 能推进并在末层末节点触发 `Victory`。
- 评估：结构对齐，能够承载 27 关战役形态。

## 2) 关卡阶段机（节点流程骨架）

- 现状：`GamePhase` 覆盖 `BuildEnemyPool -> ResetNode -> DealOpeningCards -> InteractionLoop -> ClearCheck -> RewardItemChoice -> RoomChoice -> RoomEvent -> NodeCompleted`。
- 现状：`PhaseSystem` 在 `StartNode/Attack/Pickup/UseItem/SelectReward/SelectRoom/EnterRoom` 中完成阶段推进和合法命令裁决。
- 评估：和层级系统文档的主流程基本同构。

## 3) 怪物配额规则与内容配置化

- 现状：`TableNineContentCatalog` 已落 9 条 `NodeDeckRule`（总数、L1/L2/L3、精英、层主、牌组类型）。
- 现状：`RewardSystem.BuildNodeDeckOptions` 按规则生成节点怪物池并追加精英/层主。
- 评估：数据载体已齐，具备持续调参与扩展条件。

## 4) 击杀奖励与房间基础能力

- 现状：`TriggerPoint.OnKill` 已在 `RewardSystem` 中注册，精英/层主可通过 `kill.elite`、`kill.boss` 奖池洗入战斗卡组。
- 现状：房间类型已包含 `Shop/Gold/Treasure/Fountain/Tavern`，并支持金币、满血、加血上限、奖励池等基础结算。
- 评估：基础经济与奖励链路可用。

## 5) 表现层与内核桥接方式

- 现状：表现层通过 `ShellCommandRouter` 发 Core Command，`GamePhaseFlowShellProjection` 订阅内核阶段并驱动 Screen。
- 评估：职责边界正确，符合“表现发意图，内核给事实”的设计原则。

---

## 二、关键冲突与缺口（会导致体验偏离）

## P0-1：跨节点玩家构筑未持久化（核心风险）

### 设计预期

- 玩家侧卡组应跨节点继承。
- 节点内存在“快照恢复 + 新增卡保留 + 使用后移除”的生命周期。
- 层级扩容与同名上限应约束新增卡进入。

### 当前现状

- `SetupNodeDeckAction` 每次开节点会 `deck.Clear()` 并移除非 Avatar 卡实例。
- 开局玩家帮助卡来自 `BuildNodeDeckOptions` 的默认注入，不是 Run 级持久构筑。
- `PlayerModel` 目前没有 Run 级“玩家卡组”数据结构（只有遗物/技能/金币等）。

### 影响

- 商店购买、奖励选择、掉落成长难以跨节点沉淀。
- 27 关的构筑成长主线会断裂。

---

## P0-2：生产桥接 `StartNode` 参数存在偏移与缺失

### 当前现状

- `ShellCommandRouter.SendStartNode()` 用 `run.NodeIndex.Value` 直接查节点规则（未 +1）。
- `monsterDeckId` 传空字符串，生产流程未显式携带“每层随机选中的牌组”。

### 影响

- 节点规则可能错位（或首关回退默认规则）。
- 层级“每层独立随机牌组并在该层固定使用”的设计不稳定或失真。

---

## P1-1：怪物配额“自动填充”语义与文档仍有边界差异

### 当前现状

- `BuildNodeDeckOptions` 先抽 L1/L2，再把余量导向 L3（受 L3 配置影响）。
- 在个别规则组合下，可能出现与“无 L3”节点语义的理解偏差。

### 建议

- 明确“自动”字段是“余量填充到最高可用等级”还是“仅在该等级非空时才填充”。
- 给 `NodeDeckRule` 增加单测样例覆盖节点 1/4/7 这类边界。

---

## P1-2：房间能力定义有了，但交互落地不完整

### 当前现状

- `Gold/Fountain/Treasure` 已可通过 `ResolveRoom` 结算核心效果。
- `Shop` 目前依赖 `shop.helpCards` 奖池，但目录里未发现对应池定义。
- `Tavern` 只有房间类型和权重，缺“4 选项各一次”的子流程与状态。
- `EconomySystem.DeleteHelpCard` 有能力点，但尚未见商店界面命令链路接入。

### 影响

- 房间多样性表现不足，商店/酒馆的设计价值未兑现。

---

## P1-3：房间选择阶段的表现层可见性与文档交互预期不一致

### 文档预期

- 房间卡出现后，玩家仍可处理九宫格帮助卡/道具格帮助卡。

### 当前现状

- `MainFlowDirector` 在 `RoomChoiceScreen` 时主要展示房间界面，棋盘区并非常驻可交互态。
- Core 在 `RoomChoice` 阶段其实允许 `PickupItem` / `UseItem`，表现层能力没有充分暴露。

### 影响

- 内核能力和实际可玩交互不一致。

---

## 三、综合判断：有没有能力承载？

答案是：**有能力承载，但尚未完全落地关键运行态。**

换句话说，底层路线是对的，主要问题是“战役运行态状态机”的几个关键数据和桥接参数还没全接上。

---

## 四、建议落地顺序（避免返工）

## 阶段 A（先修偏差，保证主链正确）

1. 修 `ShellCommandRouter.SendStartNode`：
   - 节点索引统一用 1-based 规则索引（或统一封装转换）。
   - 接入“每层牌组选择结果”的真实 deckId 传递。
2. 将“层内固定牌组选择”沉淀到 Run 级状态（例如 `RunModel` 扩展或独立 `RunDeckSelectionModel`）。

## 阶段 B（补运行态，建立构筑闭环）

1. 引入 Run 级玩家卡组模型（持久帮助卡清单、已移除、节点快照）。
2. 让节点开局从 Run 卡组构建 `NodeDeckOptions`，而不是只注入默认 3 张。
3. 把层级上限/同名上限约束放入奖励发放和商店购买入口。

## 阶段 C（补内容兑现度）

1. 补 `shop.helpCards` 奖池与商店购买/删牌命令链路。
2. 落地 Tavern 四选项一次性状态机。
3. 让 `RoomChoice` 阶段的棋盘/道具交互与文档一致（若确认保留该设计）。

## 阶段 D（收口验证）

1. 增加“3层 x 9节点”端到端无头回归（固定 seed 可复现）。
2. 增加房间行为矩阵测试（金币/温泉/宝箱/商店/酒馆）。
3. 增加桥接一致性测试（生产入口参数与 Headless 策略一致）。

---

## 五、现阶段一句话建议

当前不是“走偏路”，而是“主干已对、运行态待补齐”。优先把 P0 的 Run 持久构筑与 StartNode 生产桥接修正掉，再去做表现细化和房间内容扩展，性价比最高。
