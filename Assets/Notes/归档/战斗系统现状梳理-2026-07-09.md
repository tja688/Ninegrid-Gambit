# 战斗系统现状梳理（2026-07-09）

> 目的：为「更稳定的战斗重构」提供现状地图——分清**设计意图 / Core 真相 / 表现层现状**，标出断层与重构锚点。  
> 范围：节点内战斗交互（Attack / Pickup / ClickEmpty / UseItem）、相位机、Action 管线、表现同步契约；不含效果 DSL 原子细节（见 `内核效果实现质检报告-2026-07-08.md`）。  
> 对照文档：`Assets/Docs/九宫牌局/01-机制规则/战斗机制.md`、`Assets/Docs/九宫牌局-元设计/02-规则层-RUL/RUL_战斗.md`。

---

## 一、一句话结论

**Core 侧已有完整、可测的「命令 → 相位门禁 → Action 管线 → EventLog → PresentationBatch」战斗结算骨架；表现层目前是另一套「动画驱动的伪战斗」——点击怪物只播 DOTween，不发 `AttackCommand`，且击杀/旋转语义与设计和 Core 都不一致。**

稳定重构的主线应是：**让表现层成为 Core 的消费者，而不是第二套规则引擎。**

## 二、分层地图

```
┌─────────────────────────────────────────────────────────────┐
│  Flow（非 QFramework）                                        │
│  MainGameLoopManagerSingleton  →  InBattleManagerSingleton   │
│  主循环 / 入场编排 / 结算事件 stub                              │
└───────────────────────────┬─────────────────────────────────┘
                            │ StartNode / BootstrapRun
┌───────────────────────────▼─────────────────────────────────┐
│  Core（QFramework 黑盒）                                      │
│  CoreCommands → PhaseSystem → ActionPipelineSystem           │
│       → EventLog → (理想路径) CoreCommandDispatcher           │
│       → PresentationBatch + PresentationSyncSystem           │
└───────────────────────────┬─────────────────────────────────┘
                            │ 契约已定义，生产路径未接
┌───────────────────────────▼─────────────────────────────────┐
│  Cards / 表现（非 QFramework）                                 │
│  GroundCardHitProxy → FieldBattleManagerSingleton            │
│       → CardAttackBasicAdapter（纯动画）                       │
│  GroundFieldManagerSingleton（占位 / 旋转 / 补牌表现）          │
└─────────────────────────────────────────────────────────────┘
```

| 层 | 职责（应然） | 现状 |
|----|-------------|------|
| **Core** | 唯一规则真相：合法指令、伤害、击杀、旋转、补牌、通关 | 已实现；EditMode 测试覆盖 Command 壳 |
| **Core Presentation 契约** | `CoreCommandDispatcher` 把一次 Command 的 EventLog 切片成 `PresentationBatch`，锁输入直到 `PresentationFinished` | **仅测试调用**；Flow/Cards 生产代码零引用 |
| **Flow** | 跑循环、入场、等结算、推奖励/房间 | 能真实 `StartNode` 入场；循环在战斗后 `return`，奖励链路 `#if false` |
| **Cards 交战** | 消费 Batch 指令播动画，回执 FinishBatch | **独立伪战斗**：动画 + 本地 lethal 标记 + 无条件旋转 |

## 三、Core：战斗真相机

### 3.1 相位（`GamePhase`）

```
None / BuildEnemyPool / ResetNode / DealOpeningCards
  → InteractionLoop          ← 局内主交互
  → ClearCheck → NodeCompleted → RewardItemChoice
  → RoomChoice → RoomEvent →（下一节点）
  Victory / Defeat
```

`StartNode` 在 `PhaseSystem` 内同步 enqueue 一整串 Action 并 `RunToCompletion`：

1. `ClearPendingChoices`
2. `BuildEnemyPool` → `SetupNodeDeck`
3. `ResetNode` → `DealOpeningCards` → `OpeningDeal` → `FillEmptySlots`
4. `NodeStarted` → `InteractionLoop`
5. 末尾 `CompleteNodeIfCleared()`（开局即空怪时直接进奖励）

### 3.2 合法指令门禁（`RefreshLegalCommands`）

| 相位 | 合法 Command |
|------|----------------|
| 输入被 `PresentationSync` 锁住 | **仅** `PresentationFinished` |
| `None` / `BuildEnemyPool` / `NodeCompleted` | `StartNode` |
| `InteractionLoop` | `Attack` / `PickupItem` / `ClickEmpty` / `UseItem` |
| `RewardItemChoice` | `SelectReward` / `SkipHelpChoice` / `PickupItem` / `UseItem` |
| `RoomChoice` | `SelectRoom` / `PickupItem` / `UseItem` |
| `RoomEvent` | `EnterRoom` |

这是设计里「战斗结算中 / 补牌中 / 覆盖层」输入锁定的 Core 实现：**锁的是 Command 门禁，不是 MonoBehaviour 的 `_isBusy`。**

### 3.3 一次 Attack 的真实结算（`PhaseSystem.Attack`）

校验顺序：

1. 相位允许 `Attack`
2. 目标是棋盘格、非 Avatar 格、非空、是 `Monster`
3. 与 Avatar **正交相邻**（`IBoardSystem.AreAdjacent`）
4. 嘲讽等规则（`CanAttackTargetUnderRules`）

结算顺序（先攻）：

| 条件 | 管线 |
|------|------|
| 怪有先攻且玩家无 | `DealDamage(怪→玩家)` → `ConditionalDealDamageIfAlive(玩家→怪)` |
| 其余（含双方都有/都无） | `DealDamage(玩家→怪)` → `ConditionalDealDamageIfAlive(怪→玩家)` |

随后：

- `RunToCompletion()`（含 Trigger 反应栈，深度上限 64）
- 若 EventLog 自本次起出现目标的 `CardKilled` → `ResolveInteractiveRotation()`
- **未击杀则不旋转**（与 RUL / 战斗机制一致）

### 3.4 伤害 → 击杀链

```
DealDamageAction
  ├─ Rule: DamageMultiplier / DamageFlatDelta / GoldArmorAbsorb
  ├─ 护甲优先，再扣 HP
  ├─ Events: ArmorChanged / HpChanged / DamageDealt（及可能 GoldModified）
  └─ HP≤0 → FollowUp:
        Avatar → DefeatIfAvatarDeadAction
        其他 → KillIfDeadAction → KillAction
                 ├─ CardKilled + CardRemoved
                 ├─ DeactivateOwnerEffects
                 └─ ModifyGold（若有 GoldReward）
```

`ConditionalDealDamageIfAliveAction`：攻击者已进坟场 / Removed / HP≤0 则跳过——实现「先手击杀则无反击」。

### 3.5 交互旋转（三种九宫格互动共用）

`ResolveInteractiveRotation`：

```
ModifyInteractionCount(+1)
→ RotateBoardClockwise
→ FillEmptySlots
→ CompleteNodeIfCleared
```

调用方：

- `Attack`：仅当本次击杀目标
- `PickupItem`：`InteractionLoop` 下拾取后
- `ClickEmpty`：点击空格后（先 `ClickEmptySlotAction`）

### 3.6 通关

`CompleteNodeIfCleared`（仅在 `InteractionLoop`）：

```
IsNodeCleared?
→ ClearCheck → NodeCompleted → RewardItemChoice
→ OfferRewardChoice("help.choice", 3)
```

### 3.7 Action 管线语义（稳定重构必须保留的不变量）

`ActionPipelineSystem.ResolveAction`：

1. `ActionStarted`
2. **Pre** triggers
3. `Apply` → 写入 Events
4. **Post** triggers（按 Action 声明的 TriggerPoints）
5. FollowUp / Trigger 产出的 Action 进 **反应栈（LIFO）**，优先于主队列
6. `ActionFinished`

这是效果系统与战斗共用的「统一结算链」实现；重构时不要拆成表现层再算一遍。

### 3.8 表现契约（已设计、未落地）

```
CoreCommandDispatcher.Send(command)
  → architecture.SendCommand
  → PresentationBatchFactory.FromEventLog(本次切片 + CoreViewSnapshot)
  → 若此前未锁输入：PresentationSync.OpenBatch
       → IsInputLocked = batch.RequiresAcknowledgement
       → Evt_PresentationBatchOpened
  → 表现播完后 PresentationFinishedCommand(batchId)
       → FinishBatch → Evt_PresentationBatchCleared
```

`PresentationEventMap` 已把 `DamageDealt` / `CardKilled` / `BoardRotated` / `CardDealt` 等标成 `RequiresPlayback + LocksInput`。  
**生产路径没有消费者订阅 `Evt_PresentationBatchOpened`。**

## 四、表现层：当前实际在跑什么

### 4.1 入场（已接 Core）

`MainGameLoop.PlayRealBattleAsync`：

1. `BootstrapRun`（必要时）→ `InitialGameFactory`
2. `RewardSystem.BuildNodeDeckOptions` → `InBattleManager.StartBattleNodeAsync`
3. **直接** `phase.StartNode(options)`（**不经** `CoreCommandDispatcher`）
4. 按 Core 盘面快照 `PresentOpeningAsync`（牌组入场 + 格位就位）

入场后主循环立刻结束等待（`RunNodeCycleAsync` 在战斗后 `return`；奖励/房间 `#if false`）。

### 4.2 点击怪物（未接 Core）——重构最大断层

```
GroundCardHitProxy.OnMouseDown
  → FieldBattleManager.TryHandleBattleClick
  → RequestBasicAttackInternalAsync
       → CardAttackBasicAdapter.PlayBasicAttackAsync（动画）
       → 若 lethal：MarkFieldDead + VacateSlot（表现侧）
       → RotateOuterRingClockwiseWhileBusyAsync   ← 几乎总是旋转
```

要点：

| 项 | Core / 设计 | 当前表现 |
|----|-------------|---------|
| 是否发 `AttackCommand` | 必须 | **否**（全库生产无 caller） |
| 伤害 / HP | Core 算 | **不算**；lethal 靠本地 `ArmNextLethalAttack` / override |
| 反击 | ConditionalDealDamage | 有 `RequestBasicCounterAttack*`，**点击路径未自动串联** |
| 旋转 | 仅击杀 | **攻击后几乎总旋转** |
| 补牌 | Core `FillEmptySlots` | 表现侧 vacate / explore，**不同步内核牌堆** |
| 输入锁 | PresentationSync | `_isBusy` / `IsFieldBusy` 本地旗 |

结论：局内「打怪」目前是 **Explore/手感原型**，不是权威战斗。

### 4.3 拾取帮助卡

`GroundCardHitProxy` → `CardHandManager.TryPickupFromGround`——同样需核对是否走 `PickupItemCommand`（与 Attack 同类风险：表现先行）。

## 五、设计 vs Core vs 表现：差异表

| 规则点 | 设计（RUL/战斗机制） | Core | 表现现状 |
|--------|---------------------|------|----------|
| 正交相邻互动 | ✅ | ✅ `AreAdjacent` | ✅ 四向格校验 |
| 先攻决定出手顺序 | ✅ | ✅ | ❌ 无 |
| 击杀才旋转 | ✅ | ✅ | ❌ 常旋转 |
| 未击杀不旋转、可补牌 | ✅ | Attack 路径不旋转；补牌在旋转路径内 | 语义混乱 |
| **先补牌再旋转** | 设计明确「批量补牌 → 旋转」 | **先 `Rotate` 再 `FillEmptySlots`** | 表现自管 |
| 统一结算链 | 文档长链 | Action+Trigger 栈 | 动画时间轴 |
| 输入锁定 | 结算/补牌/弹窗 | PresentationSync + LegalCommands | 本地 Busy |
| 通关 → 三选一 | ✅ | `OfferRewardChoice` | 事件 stub，主循环未接 |

**Core 内部已知与设计不一致、且影响重构决策的一点：**  
`ResolveInteractiveRotation` 顺序是 **旋转 → 补牌**，设计文档是 **补牌 → 旋转**。重构前应先裁定以哪边为准（建议：改 Core 对齐设计，或改文档对齐实现，二选一写进契约测试）。

## 七、稳定重构建议（决策用，非实施清单）

### 7.1 目标架构（建议冻结为契约）

```
玩家输入
  → 表现层只做：命中检测 + 合法性预检（可选 UX）
  → CoreCommandDispatcher.Send(AttackCommand / …)
  → 若 Reject：播拒绝反馈，结束
  → 若 Accept：按 PresentationBatch.Instructions 顺序播
       Damage / Kill / Remove / Rotate / Deal / Phase…
  → PresentationFinishedCommand(batchId)
  → 解锁，进入下一输入
```

不变量：

1. **数值与规则只在 Core 变**；表现禁止 `MarkFieldDead` / 自转外环作为规则结果。
2. **一次玩家意图 = 一次 Dispatcher.Send**；禁止 `phase.StartNode` / `phase.Attack` 在 Flow 里直调（入场也应走 Dispatcher，便于开场 Batch 统一）。
3. **Busy 旗从属于 Batch 锁**；本地 `_isBusy` 只表示「正在播当前 Batch」，不能替代 `IsInputLocked`。

### 7.2 推荐落地顺序（降低翻车面）

1. **裁定旋转/补牌顺序**（设计 vs Core）→ 补一条 EditMode 契约测试。  
2. **接 Attack 生产路径**：`GroundCardHitProxy` → Dispatcher → 最小 Batch 播放器（可先只同步数字/移除，动画后挂）。  
3. **退役 FieldBattleManager 的规则职责**：lethal / 旋转 / vacate 改为 Batch 驱动；Adapter 降级为「指令执行器」。  
4. **Pickup / ClickEmpty / UseItem** 同一管道。  
5. **接主循环结算**：订阅 `OnNodeSettlementReady` 或 Batch 中的 `RewardOffered`，打开 `#if false` 的奖励/房间段。  
6. 再谈手感：先攻演出、反击时间轴、与 `CardEffectSO` 编排对齐。

### 7.3 明确不要做的事

- 不要在表现层根据动画结果「猜」是否击杀再回调 Core。  
- 不要并行维护两套 interactionCount / 旋转条件。  
- 不要为了赶手感继续扩展 `ArmNextLethalAttack` 作为正式 API。  
- 非明确需求下不要改 Core 效果原子；战斗接线优先走现有 Command/Batch。

### 7.4 与效果质检的交叉风险

`内核效果实现质检报告-2026-07-08.md` 中的 P0（临时修正不清理、裸 `OnBattle` 过宽）会在 **真正接上 AttackCommand** 后立刻暴露到局内。接线重构与效果修复应排期相邻，否则「接上权威战斗」会放大错误语义。

## 九、给重构讨论的开放问题

1. **补牌与旋转顺序**：改 Core 还是改文档？  
2. **Batch 播放器归属**：新建 `BattlePresentationPlayer`（Flow）还是扩 `FieldBattleManager`（Cards）？建议新建，避免旧伪战斗 API 污染。  
3. **入场是否强制 Dispatcher**：开场动画是否也必须等 `PresentationFinished`？  
4. **预检失败 UX**：Core Reject 与表现层「格位不可点」谁先挡——建议表现只挡明显非法，最终以 Core Reject 为准。  
5. **测试策略**：每接一条 Command 生产路径，补「Dispatcher → Event 序列 → LegalCommands」黄金用例，防止再次脱节。
