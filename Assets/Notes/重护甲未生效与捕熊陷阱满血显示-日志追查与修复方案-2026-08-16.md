## 1. Bug 1：重护甲（relic.heavy_armor）技能效果没生效

### 1.1 日志证据：挂载正常、触发正常，但很多节点没有加甲

| # | 位置 | 证据 |
|---|---|---|
| 1 | CoreLog event 1106 | `RewardChosen defId=relic.heavy_armor`（节点 2 拿到） |
| 2 | CoreLog event 1107/1108 | `RelicGranted` + `RelicMountAudit`：`mounted=2 declared=2 modifiers=1 mods=[Armor Add 1@Persistent]` —— 挂载层正常 |
| 3 | CoreLog event 1669 及后续 | 每个节点开始都有 `EffectTriggered sourceDefId=relic.heavy_armor message=relic.heavy_armor.node_start` —— 开火层正常 |
| 4 | BattleLog StartNode 快照 | 节点 3（op30）`armor=1`；节点 5（op50）`armor=3`；节点 6（op92）`armor=3`；节点 8（op148）`armor=5` —— 节点开始当前甲只等于「有效护甲重置值」，没有重护甲应给的 `floor(基础甲/2)` 增益 |

关键点：`EffectTriggered` 每关都有，说明效果在触发；但 StartNode 快照与「基础甲每 2 点加 1 当前甲」的预期不符。不是效果实例没挂，也不是 OnNodeStart 没触发。

### 1.2 代码根因：node_start 读的是裸 base Armor，而重护甲自己的 +1 是 Modifier（有效甲层）

三层护甲口径见 ADR-0028：

- 基础甲 `StatId.Armor` base：`ModifyBaseStat(Armor)` 成长写入这一层。
- 有效甲：base + Modifier（遗物/图腾等）。
- 当前甲：节点开始 `ResetCurrentArmor` 重置为有效甲。

当前内容实现：

1. `tpl.shared.4.relic_dragon_scale_armor_base`
   - 文件：`Assets/Arts/ContentVisual/tables/effect_templates.json` 与 `Assets/StreamingAssets/ContentVisual/tables/effect_templates.json` L467
   - 模板 `design_text` 写的是「基础护甲+1」
   - 实际 body 是 `{"kind":"Modifier", …, "modifier":{"stat":"Armor","op":"Add","layer":"Persistent"}}`
   - 它只加到**有效甲**，不写 `StatId.Armor` base。
   - 重护甲/龙鳞甲/泡沫甲等 8 件遗物的「基础护甲+N」都复用这个模板。

2. `tpl.relic.heavy_armor.node_start`（两个 effect_templates 的 L259）
   - body：
     `GainArmor.value = Floor(Multiply(source=Player, stat=Armor, constant=0.5))`
   - 没有 `"effective":true`，所以 `EffectValueExpression.EvaluateSource` 走 `card.Stats.GetBase(StatId.Armor)`（`EffectAtomLibrary.cs` L4822 分支）。
   - 同时写死了 `×0.5`，装配实参 `{"every":2,"gain":1}` 的 `every/gain` **没有参与计算**，描述与行为已经脱钩。

因此这局实际表现是：

- 拿到重护甲后，重护甲 +1 只让有效甲/当前甲 +1，但 base 还是 0。
- 节点 3 `floor(0/2)=0`，不加当前甲。
- 节点 4 买了第一张 `help.armor_card` 后 base 才变 1；节点 5/6/8 仍 `floor(1/2)=0`。
- 后续 base 随更多 `help.armor_card` 增长后才偶尔有增益，但玩家看到的「基础护甲 HUD」（实际显示有效甲）早已 ≥2，体感就是「技能没生效」。

### 1.3 当前代码探针复核

临时 EditMode 探针（用真实内容目录，`NineGridArchitecture.ResetForTests` + `GrantRelicAction("relic.heavy_armor")` + `PhaseSystem.StartNode`）：

| Avatar 初始 base | 有效甲 | StartNode 后当前甲 | heavy ArmorChanged delta |
|---|---|---|---|
| base=0 | 1 | 1 | 0 |
| base=5 | 6 | 8 | +2 |

即：当前代码确实是 `base/2` 取整后加当前甲；base 为 0/1 时就是零增益。

### 1.4 修复方案

**P0（推荐，局部修复）**：把 `tpl.relic.heavy_armor.node_start` 的 value 改为参数化 + 有效甲口径，与复合盔甲 `tpl.relic.composite_armor.node_start` 同一写法：

```json
{
  "kind": "Triggered",
  "trigger": { "atom": "OnNodeStart" },
  "target": { "atom": "Player" },
  "action": {
    "atom": "GainArmor",
    "value": {
      "op": "Multiply",
      "values": [
        {
          "op": "Floor",
          "values": [
            {
              "op": "Divide",
              "values": [
                { "source": "Player", "stat": "Armor", "effective": true },
                { "constant": "{{every}}" }
              ]
            }
          ]
        },
        { "constant": "{{gain}}" }
      ]
    }
  }
}
```

落点：`Assets/Arts/ContentVisual/tables/effect_templates.json` L259 与 `Assets/StreamingAssets/ContentVisual/tables/effect_templates.json` L259 **同步改**。

探针验证：改后 base=5 + 重护甲（有效甲 6）→ StartNode 后当前甲 9（`floor(6/2)=3`），与玩家看到的「基础护甲 6」一致；base=0 时仍为 1（合理，2 点才给 1）。

**P1（语义更严格但面更大的替代）**：如果策划坚持「基础护甲」严格按 ADR-0028 = base 层，则应改共享模板 `tpl.shared.4…`，把 `kind:Modifier` 改成 `OnActivate + ModifyBaseStat(Armor)`（或给重护甲单独挂一条真正写 base 的 OnActivate 装配）。这样 base 层才会包含遗物给的「基础护甲+N」，heavy 保持读 base 才自洽。
代价：共享模板影响 8 件遗物，需全量重跑遗物/护甲回归；且要重新确认这些遗物此前「Modifier 加成」是不是有意设计。

**P2 回归护栏**：新增 `HeavyArmorNodeStartTests`，直接仿照 `RelicCompositeArmorNodeStartTests`：
- base 0 + 重护甲 → StartNode 当前甲 1；
- base 5 + 重护甲 → StartNode 当前甲 9（若 P0 落地）；
- 修改 `every/gain` 实参后，加甲量随实参变化（锁死描述与行为同源）。

## 2. Bug 2：捕熊陷阱被怪物卡触发后，Core 扣血正确但怪物卡显示满血

### 2.1 日志证据：伤害发生在发牌表演完成之前

最清晰的样本在节点 21，捕熊陷阱 uid=424：

| # | 位置 | 证据 |
|---|---|---|
| 1 | CoreLog event 21391 | `EffectTriggered sourceDefId=trap.bear_trap cardUid=424 message=trap.bear_trap.fill` |
| 2 | CoreLog event 21394 | `BoardStepBegin requestId=720 stepIndex=0 stepKind=Deal dealCount=1` |
| 3 | CoreLog event 21395/21396 | `DealAttempt/DealResult uid=413 slot=8` —— 新怪 `monster.ringleader` 补入陷阱邻格 |
| 4 | CoreLog event 21398 | `BoardStepBegin requestId=720 stepIndex=1 stepKind=Remove`（移除捕熊陷阱 424） |
| 5 | CoreLog event 21412 | `CardFaceBaseStatCommit uid=413 stat=Attack hasView=1`；**没有** `BaseStatModified stat=Hp` 的对账补救 |
| 6 | BattleLog op629 | 稍后该怪参与敌方行动时 `attacker.uid=413 hp=1` —— **Core 血量已经被捕熊打到 1** |

也就是说：Core 在 `FillEmptySlots` 批次里已经正确结算了捕熊陷阱的 10 点伤害；但表现层在 `Deal` 步才把怪物视图发上场，伤害指令落在 Deal 之后、Remove 之前的表演间隙里。

### 2.2 代码根因：Impact 先提交减血，Settled 的 CardDealt 又把满血盖回去

锚点表（`PresentationEventMap.cs`）：

- `HpChanged` → `PresentationBeat.Impact`（L55）
- `CardDealt` → `PresentationBeat.Settled`（L64）

补牌批的表演顺序（`BoardPresentationPlayer.DrainBoardStepsAsync`）：

1. `step[0] = Deal`：`DrainDealsAsync` 先把 uid=413 的视图从牌组飞上盘。此时 `CoreCardPresentationMapper.ApplyToManagedCard` 只刷视觉、不提交三围。
2. `step[1] = Remove`：在首个 Remove 前调用 `FlushImpactExcept(TriggerEffect)`（L396-399），把捕熊的 `DamageDealt/HpChanged` 派发给 `CardFaceStatHandler`。
3. `CardFaceStatHandler.ApplyHp` 在 uid=413 的视图上提交了**扣血后的 HP**。
4. 本批 `PresentStep` 走到 Settled 时，同一批更早的 `CardDealt` 指令才被消费；`CardFaceStatHandler.ApplySpawnFace`（L326-340）**无条件**用生成事件的 `RemainingHp`（满血）再提交一次，覆盖第 3 步的减血值。

为什么统一对账缝没有救回来：

- `CardFaceLedgerModel` 是按事件日志顺序重放的：`CardDealt(满血) → HpChanged(残血)`，账本最终 = 残血，与 oracle 一致，因此不会补发 `BaseStatModified(Hp)`。
- 表现层实际不是按事件日志顺序重放，而是按 `Impact` / `Settled` 两个锚点分批派发：同批内 Impact 永远先于 Settled。于是「后发生」的 HpChanged 先上屏，「先发生」的 CardDealt 后上屏并覆盖。
- ConsoleLog 中 uid=413 没有 `[CardFaceStatHandler] UpdateHp 找不到卡面`，说明视图确实已经存在、减血确实上过屏；问题就是随后被满血生成值覆盖。

同机制也解释了 ConsoleLog 15:16:34 起 uid=411 的一串 `UpdateHp/ModifyBaseStat 找不到卡面`：那是另一条更极端的时序（Impact 早于视图存在，指令直接 miss），与本 bug 同类但不同分支。

### 2.3 修复方案

**P0（推荐，最小且通用）**：让生成类指令只填「尚未提交」的通道，不覆盖同卡已经由 Impact 提交过的血/甲。

给 `CardPresentationSnapshot` 增加通道已提交标记（推荐）：

```csharp
public bool HasAttack;
public bool HasArmor;
public bool HasHp;
public bool HasActionCount;
```

`CardFaceStatHandler.CommitNumeric` 在写入每个非 null 通道时同步置位对应 `Has*`；所有快照拷贝点（`CardFaceStatHandler.CloneSnapshot`、`CoreCardPresentationMapper.ApplyVisualsPreservingCommittedStats`、`CardFaceFlipBeatHandler` 等）保留这些位。

`ApplySpawnFace` 改为：

```csharp
var previous = card.CommittedPresentation;
CommitNumeric(
    card,
    attack: previous == null || !previous.HasAttack ? Mathf.Max(0, gameEvent.ResultValue) : (int?)null,
    armor: previous == null || !previous.HasArmor ? Mathf.Max(0, gameEvent.RemainingArmor) : (int?)null,
    hp: previous == null || !previous.HasHp ? Mathf.Max(0, gameEvent.RemainingHp) : (int?)null,
    actionCount: null);
```

效果：
- 正常新卡首发：`previous == null`，所有通道照常由 CardDealt 填满，现有表现不变。
- 捕熊/同类补牌触发伤害：`HpChanged` 先提交过 HP，Settled 的 CardDealt 只补攻击等未提交通道，**保留已提交的残血**。
- 已存在于场上的卡重放生成事件时，也不会用旧生成值覆盖更新后的血/甲。

**P1（可选，等价兜底）**：如果不想加标志位，可在 `ApplySpawnFace` 里对 `card.CommittedPresentation != null` 的卡保留 `Hp/Armor` 两个 Impact 通道，只填 `Attack`。但快照里的 int 默认 0 无法区分「未提交」和「已提交为 0」，所以正式实现建议用 P0 标志位。

**P2 回归护栏**：
- 单测 `CardFaceStatHandler` 语义：模拟 `CardDealt(满血) → HpChanged(残血)` 后按 `Impact → Settled` 派发，最终卡面 HP 必须为残血。
- 复用/扩展 `CardFaceReconciliationRegressionTests.ReplayFaces` 的模拟器，锁定「生成事件不得覆盖已提交通道」。
- QuickTest `\6`（捕熊通道）人工复验：邻格补真怪后，若怪未死，卡面血量应立即显示捕熊后的残血并保持。

## 4. 不做的事

- 不把 `DealDamage/HpChanged` 改成 Settled：命中帧扣血是既有体验契约（ADR-0005/0048/0050），不能为补牌特例回退。
- 不让表现层回头读 Core 对账：继续维持单向指令链（ADR-0045）。
- 重护甲若走 P0，暂不动共享模板 `tpl.shared.4…`，避免 8 件遗物面扩散；是否要严格 base 语义留给策划拍板。
