调查完成，临时脚本已清理。下面是我找到的东西。

结论：这不是一个 bug，是一条缺失的不变量
你的设计意图（「有空地 + 卡组有卡 → 补牌」）在代码里根本不存在。它不是一条被某处实现错了的规则，而是从来没有被表达成规则——它被拆成了 10 条剧本各自手工排队的补牌批次。所以现象必然「时好时坏」：补不补取决于你恰好走了哪条剧本分支。

三份证据（两路 opencode 子代理 + 我自己的日志取证）指向同一个根：

Core 侧 FillEmptySlotsAction 全仓只有 3 个生产入队点（PhaseSystem.cs:172 开局、:1813 击杀后、:1845 drain/fusion），TriggerSystem 上没有任何 OnKill→Fill 的系统级触发器，pipeline 收尾没有自动 Fill。「场上有空地就补牌」在 Core 里不是不变量，只是表现层调度器的一个选择——连「只在 InteractionLoop 补牌」这条都写在 DrainRefillScheduler.cs:90，而不在 Core。

你抓到的三个现象，各自的机制
现象 1（节点三开局有空缺不补）——已在你的日志里坐实，而且比你想的更严重

corelog 里 18 次 StartNode 的 boardOccupantCount：17 次是 8，只有节点 3 是 7，而同时 deckCount=14（抽牌堆有 14 张）。逐格快照 1:O55|2:O63|3:O53|4:O0|6:O50|7:O43|8:O44|9:O42 —— 格 4 空，且 coreCount=7。

注意 coreCount=7：Core 自己就只有 7 张。这不是表现层丢视图，是 Core 的补牌只填了 7 格。机制在 BoardDeckActions.cs:371-397：FillEmptySlotsAction 按顺时针只遍历一圈，遍历结束后才派发 OnDeal/OnEnter 触发（:410-413）。而节点 3 格 2 是 trap.rolling_stone——补牌批内被触发的效果腾出的格，本批不会再补，而 StartNode 之后没有任何收尾 Fill 命令。于是空格一直挂到你第一次交互。这也正好解释了你说的「点一下那个空格就正常补牌+旋转」：explore 剧本带 Fill 批。

现象 3（捕熊陷阱 / 恐怖面具 时好时坏）——同一个根，不同触发点

捕熊陷阱 tpl.trap.bear_trap.fill 的触发条件就是 ActionSource(action=FillEmptySlots)——它专门在补牌批里开火，打完还 RemoveCard(Self) 自移除。也就是说它必然落在「补牌循环已跑完」之后。战斗中靠敌方行动收尾（ResolveEnemyActionFinale）兜底补一次，所以「有时补」；一旦场上没有参与敌方行动的怪，EnemyActionPhaseScheduler.cs:51 就早退，收尾补牌也没了，于是「有时不补」。

你说的遗物是恐怖面具 relic.terror_mask（击杀 6 只 → 随机移除 1 只非 Boss 怪）。日志里三次触发（节点 19/21/24）我都追了后续事件——这三次都补上了，因为它挂在 OnCumulative，触发时机在玩家交战批内，晚于它的 ResolvePostKillFill 会补。所以它单独不是漏点，但它和捕熊陷阱叠在一起就是：捕熊在 Fill 批里打死一只怪 → OnKill 链拉起恐怖面具 → 又拆走一只怪 → 两个洞都在 Fill 批内，都不补。这正是你感觉「触发很随机」的来源。

另外还有一个判定口径不一致的独立漏点：攻击路径用 ContainsCardKilled(targetUid) 只看目标死没死，用牌路径用 ContainsAnyCardKilled 看任意卡。所以「攻击没杀死目标、但同批效果杀死了别的怪」时，攻击剧本走非击杀分支，没有 DrainRefill（AttackIntentScriptFactory 里根本没注入 DrainRefillScheduler，与 UseItemIntentScriptFactory 不对称）。

现象 2（节点三战斗末尾红色错误）——日志里没找到 Error/Exception，但找到了两类被降级成 Anomaly 的东西

registrylog 里有 163 次 FieldVisualGap 和 51 次 ChoreoIncompleteAtBeatClose。我按 coreCount != occupiedCount 过滤掉中间态噪声后，剩 27 次真实 Core/表现占格分叉。另外全局 3 次发牌失败 ok=false reason=nullView（节点 3 idx2166、节点 10、节点 21）——Core 已经补了牌，表现层因为 View 为空画不出来，然后回滚清占格。这是「Core 有牌、屏幕没牌」的第二类空缺，与补牌漏排是两回事。你看到的红色警告很可能是这批 Debug.LogWarning（CardDeckManagerSingleton.cs:1189），不是 Exception。

现在开始拷问
要从一个「统一的根」上解决，有几个决定只有你能做。这些是当前前沿上、不依赖其他未定问题的：

❓ Q1 - 「补牌」到底是谁的不变量：现在它是表现层剧本的编排选择。要收口，有三种根本不同的做法：(a) Core 不变量——在 ActionPipelineSystem 每次 RunToCompletion 收尾处，若「相位=InteractionLoop 且未清关 且有空格 且抽牌堆非空」则自动补到不动点，表现层剧本里所有 Fill/Drain/Fusion 排队全部删掉；(b) 导演层单一兜底——保留 Core 现状，但在 PresentationDirector.Tick 里当主线跑空且无缓冲时检查空格，缺则自动追加一个补牌批；(c) 维持逐剧本排队，只把三个漏点各自补上。

➡️ 我建议 (a)。理由：你的痛点正是「太多、太杂、触发很随机」，而 (b) 和 (c) 都保留了「每新增一条产生空格的路径就要记得手工挂 Fill」这个结构，漏点会持续再生。(a) 把它变成一条 Core 层不可绕过的事实：批次结束时盘面不得同时存在空格和可补的牌。代价是补牌时序从「剧本显式声明」变成「隐式收敛」，ADR-0001 Batch-ack 的批次边界语义需要重新表述。

❓ Q2 - 补牌应该补到「一圈」还是「不动点」：现行 FillEmptySlotsAction 只遍历一圈就收工，然后才派发 OnDeal/OnEnter——这正是节点 3 空格的直接机制。要么改成循环直到「无空格 或 牌堆空 或 达到迭代上限」，要么保持一圈但在触发链之后再排一次 Fill。前者要面对无限循环风险：捕熊陷阱补一张就杀一只再自移除，理论上能把整个牌堆吃光（这在规则上其实是合理的——陷阱确实该一张张吃）。

➡️ 我建议补到不动点，但设迭代上限（例如 16 轮，超限记 Anomaly 而不是抛异常）。理由：「有空地就补」本来就是不动点语义，一圈是实现细节泄漏。上限只是防御 ActionPipelineSystem 那种 depth>64 式的自我保护，正常内容不该碰到。

❓ Q3 - 捕熊陷阱在「开局补牌」里该不该开火：它的触发条件写死 ActionSource=FillEmptySlots，所以开局铺满 8 格的过程中它必然对邻格开火（10 点伤害，一层弱怪普遍撑不住），玩家还没操作就已经掉了一只怪 + 陷阱自爆。这是设计意图，还是「补牌」这个词在开局和战中被当成同一件事的意外后果？

➡️ 我建议开局 Fill 静默机关触发，即区分「开局铺场」与「战中补位」两种 Fill 语义。理由：开局盘面是玩家的初始信息，在他有任何输入之前就自行连锁反应，既不可预期也不可回应；而且这正好是节点 3 现象的源头。但这是策划口径，我不替你定。

❓ Q4 - FieldVisualGap / ChoreoIncompleteAtBeatClose / nullView 该不该升级为硬失败：现在它们是 Anomaly + LogWarning，一次游玩攒了 163 + 51 + 3 条，没人看。你报告的「红色错误」大概就在这里面。

➡️ 我建议：把 coreCount != occupiedCount 的真分叉（27 次）升级为开发期 Assert，nullView 发牌失败升级为必须重试或显式 Anomaly 上屏；coreCount == occupiedCount 的中间态噪声（136 次）则应当从 Gap 判定里剔除——它们把真信号淹了。理由：占格分叉是 ADR-0001 明令禁止的双真相，静默 warning 等于放弃这条不变量。

❓ Q5 - 修复的验证门槛：这类「随机复现」的问题，靠再玩几局验证不可靠。可选：(a) 写 EditMode 契约测试，用固定种子构造「Fill 批内触发移除」场景，断言批次结束后无空格；(b) 加一条运行时不变量检查（每次 idle 时断言「无空格 或 牌堆空」），跑几局看 Anomaly 是否归零；(c) 两者都做。

➡️ 我建议 (c)，且先写 (b)。理由：(b) 能立刻把「还有多少我没抓到的漏点」变成可数的数字——你现在最痛的就是不知道漏点有多少。有了它，(a) 的测试用例可以直接从实测捕获的场景反推，而不是靠想象枚举。
