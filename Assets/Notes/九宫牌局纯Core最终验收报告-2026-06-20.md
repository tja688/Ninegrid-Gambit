## 当前强项

### 1. 旧 P1 缺口已经补上

归档 QA 报告中提到的两个关键口子，在当前代码里已经有实质闭环：

- **Command -> Batch -> 输入锁**：`CoreCommandDispatcher.Send()` 会记录 EventLog 起点、执行 QFramework Command、生成 `PresentationBatch`、捕获 `CoreViewSnapshot`，并在非锁定且非 `PresentationFinishedCommand` 时打开 `PresentationSyncSystem`。
- **owner 生命周期注销**：`RemoveCardAction`、`KillAction`、`PickupCardAction` 会追加 `DeactivateOwnerEffectsAction`；`SetupNodeDeckAction` 会先 `DeactivateNonAvatarRuntimeEffects`，避免上一节点非 Avatar runtime effects 跨节点残留。

### 2. 单一流水线是真落地，不是命名占位

`ActionPipelineSystem.ResolveAction()` 当前顺序为：

1. 写入 `ActionStarted`
2. 分发 Pre triggers
3. 执行 `action.Apply()`
4. 将 result events 写入 EventLog
5. 分发 Post triggers
6. 解析 follow-up actions
7. 写入 `ActionFinished`

触发产生的动作会反向压入 reaction stack 并立即深度优先解析；这和架构设计里的“反应栈表达因果链”一致，并且已有 `ReactionStackResolvesDepthFirstAndKeepsOrderedEventLog` 测试覆盖。

### 3. 内容落地规模已经超过“样例阶段”

当前测试断言的 Luban/生产内容规模：

- Cards：87
- Effects：141
- Skills：68
- Relics：19
- MonsterDeck / Reward / Room / NodeDeckRule 均有生产表入口

`P6ContentLandingTests` 覆盖了多批帮助卡、遗物、玩家技能、怪物技能 DSL；`P6LubanContentTests` 覆盖 Luban catalog 与 hardcoded catalog 的一致性。

### 4. 表现层已经可以直接消费 Core

Core 里已经有最小可用表现契约：

- `CoreCommandDispatcher`
- `CoreCommandDispatchResult`
- `PresentationBatch`
- `PresentationInstruction`
- `PresentationEventMap`
- `CoreViewSnapshot`
- `ActionLogProjector`
- `RecordingPresentationAdapter`
- `PresentationFinishedCommand`

这意味着表现层第一版不需要直接碰 PhaseSystem / ActionPipeline / EventLog 游标，可以从 dispatcher 开始。

### 5. 无头真局测试基础已经具备

`HeadlessCampaignDriver` 真实走 Command 通道，能从开局推进到 Victory/Defeat；`RandomAgent` 只选择合法具体命令；`HeadlessInvariantChecker` 做首批低误报红灯；`RunTranscriptWriter` 输出人类可读战报；`HeadlessBatchRunner` 能导出 CSV/JSON 指标。

这已经满足“后续根据策划设计大规模跑用例”的基本技术前提。

## 剩余风险

| 等级 | 风险 | 影响 | 建议 |
|---|---|---|---|
| P1 | `UseItemCommand` 只传 `itemUid`，而 `UseItemAction` 支持 `selectedCardUids/selectedOption` | 表现层遇到需要选目标/选项的帮助卡时，无法走公开 Command 完整表达意图 | 新增重载或新 Command：`UseItemCommand(int uid, IReadOnlyList<int> selectedCards, string selectedOption)` |
| P1 | `CoreViewSnapshot` 当前板面 HP/Armor/Attack 用 base stats | UI 如果显示有效攻击/条件光环，可能和实际结算不一致 | Snapshot 增加 effective stats，或提供表现层只读 query/facade |
| P2 | `CoreGameEvent` 是通用字段包 | 表现适配器需要按事件类型理解字段语义，容易误用 `Amount/Delta/TargetUid/CardUid` | 为每个事件补 payload 语义文档，或逐步引入 typed payload / event schema |
| P2 | Model 写 API 仍是 public | Presentation 引用 Core 后理论上能绕过 Command 写模型 | 新增 Presentation guard；中期考虑写 API internal 化或集中到 mutation service |
| P2 | 部分 `RuleId` 是预留但未被消费 | 例如 `InteractionDistance`、`GoldCostOffset` 目前没有明确查询点，不能把枚举存在等同于规则已落地 | 每新增 RuleModifier 必须同时补“消费点 + 测试” |
| P2 | 内容特化原子主要在 Core | Core 会随内容扩展变厚 | 原型期可接受；后续可拆通用 Core atoms 与 Content-specific atoms |
| P3 | PhaseSystem 是 enum/switch，不是 FSMKit | 流程继续膨胀后可维护性下降 | 当前可保留；房间/商店/事件分支复杂化后再迁 FSM |

## 是否达到架构设计最终验收标准

按“纯 Core 现在能否承载表现层、内容 DSL、自动化测试和确定性回放”的标准：**达到**。

按“未来任意策划效果都数据化、不再触碰 Core”的绝对标准：**接近，但不应宣称完全达到**。原因是 RuleModifier 的消费点、少数表现意图参数、事件强类型契约仍需要继续加固。

我建议把当前状态定义为：

**Pure Core 1.0 验收通过，允许进入表现层集成与大规模用例测试；后续 Core 工作重点从“搭骨架”转为“契约加固 + 用例驱动补边界”。**

## 下一步建议

1. 先补 `UseItemCommand` 的目标/选项参数，避免表现层一接帮助卡就绕过 PhaseSystem。
2. 给 `CoreViewSnapshot` 增加 effective stat 字段，表现层默认用 snapshot，不直接猜属性。
3. 为 39 个 `CoreEventType` 补字段语义表，并把表现适配器按语义表验收。
4. 加 Presentation guard：禁止表现层调用 Model 写方法、Action Apply、System mutation API。
5. 将每个新策划效果要求落成：DSL 校验测试 + 最小场景 replay + headless forced card 回归。
