我认真看完了这份探查文档。先给结论：

## 我的判断

**“是否补牌、补哪些位置、补到什么状态、补牌触发哪些规则”必须属于游戏 Core。**

**“补牌什么时候开始播放、每张牌飞多久、是否逐张展示、镜头怎么移动、玩家什么时候重新获得操作权”属于表现层。**

所以这不是简单地在 Core 和表现层之间二选一，而应该是：

> **Core 决定事实，表现层决定事实如何被看见。**

就你目前的三种方案而言，我支持文档中的 **(a) Core 不变量**，但我会对具体落点做一个重要修正：

> 不建议把补牌粗暴地塞进每一次 `RunToCompletion` 的通用尾部；更合适的是，在 Core 中建立一个明确的“结算至稳定状态（Stabilize / Settle）”阶段。

你这次的问题确实不只是几个补牌调用漏了。文档已经把根因说得很准确：你的设计意图从未被表达成一条系统规则，而是分散在不同剧本中手工排队，因此新路径越多，漏点只会越来越多。

---

# 一、为什么补牌必须归 Core

判断一条逻辑应该属于 Core 还是表现层，可以问几个问题：

1. 它是否会改变游戏的合法状态？
2. 它是否会影响随机数、牌堆、触发器或战斗结果？
3. 存档、读档、回放、AI 模拟、自动测试时是否需要它？
4. 即使完全关闭画面，这条规则是否仍应成立？

补牌对这四个问题的答案都是“是”。

补一张什么牌会改变牌堆顺序；补出的牌可能触发 `OnDeal`、`OnEnter`；捕熊陷阱可能攻击并自毁；恐怖面具可能继续移除怪物；这又可能制造新的空位。这些都不是动画效果，而是**游戏状态演算**。

表现层如果决定“这次要不要补”，实际上就意味着：

* 画面调度器参与决定游戏规则；
* 跳过动画、加速动画或者表现异常，可能改变最终游戏状态；
* Headless 测试和正式游戏可能跑出不同结果；
* 回放必须复现表现层的调度细节才能保证一致；
* 每增加一种产生空格的新机制，都要记得给某个剧本挂补牌。

这正是现在“有时补、有时不补”的结构性来源。

---

# 二、真正需要定义的不是“什么时候调用 Fill”，而是“什么叫合法稳定状态”

目前系统的思维似乎是：

> 某个行为杀死了一张牌，所以接下来排一个 Fill。

这种设计的问题是，它要求调用者知道所有后果。

但在效果链系统里，调用者不可能可靠地知道：

* 攻击杀死目标；
* 死亡效果移除另一张牌；
* 遗物再移除一张牌；
* 新补出的陷阱又杀死一张牌；
* 陷阱自毁再制造一个空位。

因此不应该围绕“哪条路径需要补牌”设计，而应该围绕**状态收敛**设计。

我建议定义这样的 Core 不变量：

> 当游戏处于允许补牌的稳定边界时，如果节点尚未结束、牌堆仍有可发牌、周围存在可补空位，则系统必须继续结算，直到不存在可补空位，或者牌堆无法继续补牌。

关键是“稳定边界”。

### 不变量不应该要求每个瞬间都满足

动画过程中、攻击处理中、死亡效果处理中，出现空位完全正常。不能一出现空位就立刻插入补牌，否则会造成：

* 攻击尚未结算完就插入新牌；
* 多个死亡效果之间穿插补牌；
* 触发顺序变得难以预测；
* 玩家看见牌被补上后，又被尚未播放的旧效果打掉。

因此它不是：

> 任何时刻都不得有空格。

而应该是：

> **当当前玩家意图及其派生效果全部结算完成，系统准备重新进入可交互状态时，不得同时存在“可补空位”和“可用牌”。**

这是一条**稳定态不变量**，而不是瞬时不变量。

---

# 三、我建议的 Core 流程：意图、效果链、稳定化、提交

建议把一次玩家操作明确分成四个阶段。

```text
1. Execute Intent
   执行攻击、拾取、使用卡牌等原始意图

2. Resolve Consequences
   处理伤害、死亡、移除、遗物、陷阱、OnKill、OnCumulative 等派生效果

3. Stabilize Board
   检查盘面是否满足稳定态不变量
   若有空位且可以补牌，则发牌
   处理新牌产生的 OnDeal / OnEnter 效果
   若又出现空位，则继续稳定化

4. Commit Stable State
   确认节点是否结束
   输出稳定状态
   重新允许玩家操作
```

这样一来，`AttackIntentScriptFactory`、`UseItemIntentScriptFactory`、敌方行动、陷阱、遗物都不再需要知道自己是否应该排 `DrainRefill`。

它们只需要做自己的领域行为：

* 攻击系统负责攻击；
* 死亡系统负责死亡；
* 遗物系统负责遗物效果；
* 盘面稳定器负责使盘面收敛。

这在工程上叫做**职责闭合**：每个模块只负责它拥有的信息。

---

# 四、为什么我不完全赞成“每次 RunToCompletion 尾部自动 Fill”

文档提出在 `ActionPipelineSystem.RunToCompletion` 收尾自动补牌，这个方向是对的，但“每次”可能过于宽泛。

`RunToCompletion` 如果同时用于：

* 一个原子 Action；
* 一组触发器；
* 一次局部子批次；
* 整个玩家意图；

那么在所有尾部自动补牌，会把补牌插入到过细的边界中。

例如：

```text
玩家攻击
→ 目标死亡
→ 执行 OnKill
→ 此时某个子 RunToCompletion 结束
→ 自动补牌
→ 再继续处理恐怖面具
```

这就可能导致补牌发生得太早。

所以最好不是“任意 Pipeline 收尾”，而是引入一个语义明确的边界：

* `ResolveIntentToStableState`
* `SettleInteraction`
* `BoardStabilizationPhase`
* `ResolveUntilQuiescent`

名称不重要，重要的是它表达：

> **当前外部意图及其所有派生后果已经处理完，现在开始恢复游戏稳定态。**

也就是说，补牌应该是 Core 的规则，但必须放在正确的**领域事务边界**，不能只是放在一个碰巧方便的基础设施函数末尾。

---

# 五、“补一圈”还是“补到不动点”

这里我强烈赞成文档的判断：**补到不动点。**

当前只遍历一圈的问题，本质上是把一个实现细节错误地当成了规则。文档记录的节点三案例正是：先填一圈，随后 `OnDeal/OnEnter` 才制造新空位，但这一批已经结束，于是空位永久残留。

如果游戏规则是“空位应被补满”，那么正确语义一定是：

```text
重复：
    补当前空位
    处理补牌造成的全部效果
直到：
    没有空位
    或牌堆为空
    或当前状态不允许补牌
```

不过我不太建议只使用一个固定的“16 轮上限”作为主要安全机制。固定上限可以保留，但还可以做得更严谨。

## 更好的安全保护

每轮稳定化记录：

* 牌堆数量；
* 盘面占用；
* 当前待处理 Action 数；
* 状态摘要或状态哈希；
* 已执行的稳定化 Action 数量。

然后检查：

### 1. 单调进展

正常补牌链中，牌堆应持续减少，或者待处理事件持续被消费。

如果：

* 有空位；
* 牌堆未减少；
* 盘面未变化；
* 待处理队列也未变化；

就说明系统卡住了，不应该继续空转。

### 2. 状态循环检测

如果稳定化期间再次出现完全相同的状态摘要，说明发生循环。

### 3. Action Budget

例如每次玩家意图最多允许稳定化处理 128 或 256 个派生 Action。超过后：

* 开发环境直接 Assert；
* 正式环境记录高优先级 Anomaly；
* 不要悄悄把一个非法半稳定状态当成正常状态继续玩。

如果游戏不存在“把牌重新塞回抽牌堆”或无限生成牌的机制，其实牌堆数量本身就是天然的终止度量：每补一张，牌堆减少一张，过程必然终止。只有当系统可以无限造牌、回收牌或复制牌时，才真正需要复杂的循环防护。

# 六、开局铺场和战中补位应该拆成不同的领域语义

这一点非常重要。

虽然两者在视觉上都是“把牌发到空位”，但领域含义并不相同：

### 开局铺场

* 建立初始盘面；
* 玩家尚未获得控制权；
* 可能希望初始信息稳定、可阅读；
* 某些机关是否触发，需要明确策划规则。

### 战中补位

* 是一次交互造成的后续变化；
* 新牌进入场地可能触发效果；
* 玩家可能需要看到完整的因果链。

所以不建议所有东西都只叫：

```text
FillEmptySlots
```

至少应该携带一个 Core 可见的原因：

```text
FillReason.InitialLayout
FillReason.PostInteraction
FillReason.EffectResolution
FillReason.NodeTransition
```

触发器也不应该只匹配：

```text
ActionSource == FillEmptySlots
```

而应该能表达：

```text
OnCardEnteredBoard
且 EntryReason == PostInteractionRefill
```

这样“捕熊陷阱开局是否开火”就不再依赖表现层做特殊处理，而是一条清楚、可测试的游戏规则。

我个人也倾向于：

> 开局铺场默认不触发带有攻击性或自毁性的“战中入场机关”，除非某张牌明确声明它会在初始生成时触发。

但这部分确实是策划选择，不是纯架构判断。

---

# 七、表现层该管理什么

表现层仍然非常重要，只是它不应该管理“是否发生补牌”。

它应该管理：

* 卡牌从牌堆飞到格子的轨迹；
* 顺时针还是同时发牌；
* 每张牌之间的间隔；
* 镜头和音效；
* 攻击、死亡、遗物、补牌的展示顺序；
* 玩家输入锁；
* 动画加速和跳过；
* 表演失败后的视图恢复。

比较理想的结构是：

```text
Core:
    生成确定性的领域事件序列

Presentation:
    消费领域事件序列并播放
```

例如 Core 输出：

```text
CardKilled(uid=12)
RelicTriggered(terror_mask)
CardRemoved(uid=17)
RefillStarted(reason=PostInteraction)
CardDealt(uid=31, slot=4)
CardEntered(uid=31, slot=4)
TrapTriggered(uid=31)
DamageApplied(...)
CardRemoved(...)
CardDealt(...)
BoardStabilized
```

表现层可以逐条播放，但不能决定跳过其中的 `CardDealt`。

如果动画需要控制 Core 的推进节奏，可以使用 Ack：

```text
Core 产生下一组语义事件
→ 表现层播放
→ 表现层 Ack 已完成展示
→ Core 继续开放下一组事件
```

但这里必须严格区分：

> Ack 控制“什么时候继续展示”，不控制“游戏规则是否执行”。

---

# 八、Core 与表现层不一致的问题，必须单独治理

文档指出还有第二类问题：Core 已经补了牌，但表现层因为 `nullView` 没画出来，并且出现回滚清占格。这与 Core 漏补是两个不同的问题。

这里的原则应该非常硬：

## 表现层不得通过回滚 Core 来掩盖视图失败

如果 Core 的状态是：

```text
slot 4 = card 31
```

但 View 创建失败，正确处理方式应该是：

1. 重试创建 View；
2. 使用占位 View；
3. 从 Core Snapshot 重建整块盘面；
4. 开发环境立即 Assert；
5. 正式环境显示可诊断错误并尝试恢复。

不应该做：

```text
View 创建失败
→ 把 slot 4 在游戏状态中清掉
```

因为这相当于让渲染资源是否加载成功决定游戏规则。

更精确地说：

* **Core 是权威真相；**
* View Registry 是派生缓存；
* 派生缓存坏了，应从权威状态重建；
* 不得反过来修改权威状态以适配缓存。

只有在 Core 自己执行发牌失败，例如目标格非法、牌堆无牌时，才能回滚 Core 事务。

# 九、对三种方案的评价

## (a) Core 不变量

**正确的长期方案。**

优点：

* 所有产生空格的路径自动覆盖；
* 新内容不需要手工记得挂 Fill；
* Headless、存档、回放和测试一致；
* 能清楚定义最终稳定态；
* 大幅降低随机漏点。

风险：

* 需要重新定义批次边界；
* 需要明确开局和战中补位语义；
* 需要重新梳理事件和动画 Ack；
* 一次性改动较大。

我的评分：**9/10**。

---

## (b) 表现导演层统一兜底

可以作为**迁移期的监控或补救措施**，不应作为最终规则。

它确实比十几个剧本分别排 Fill 好，因为至少收口到了一个位置。但它仍有根本问题：

* 无表现层运行时，规则不成立；
* 动画暂停、导演卡住会导致游戏状态不完整；
* 回放和自动测试需要模拟导演；
* Core 允许长期存在不合法状态；
* 表现层仍在决定牌堆消耗和触发链。

它适合暂时做：

```text
发现 Core 已稳定但仍有可补空位
→ 报 Critical Anomaly
```

不适合长期做：

```text
发现空位
→ 表现层主动修改游戏状态并补牌
```

我的评分：**4/10，作为临时护栏可到 6/10**。

---

## (c) 继续逐剧本补漏

只能作为紧急热修。

它会迅速解决眼前几个已知案例，但没有消除漏点产生机制。文档中攻击路径和用牌路径判定不一致，就是这种模式自然产生的结果。

未来再加入：

* 连锁爆炸；
* 推挤；
* 召唤替换；
* 吞噬；
* 牺牲；
* 清场遗物；
* 特殊地形；

每个功能都可能再次漏排 Fill。

我的评分：**2/10，紧急版本止血可用**。

---

# 十、我会怎么落地

建议按下面的顺序迁移，而不是一次把所有旧 Scheduler 全删掉。

## 第一阶段：先建立可执行的不变量

在 Core 加一个只检查、不修复的断言：

```text
当系统进入 InteractionIdle 时：

若
    node 未结束
    且 phase 允许补牌
    且 deck 有牌
    且 board 有可补空位

则记录 RefillInvariantViolation
```

这一步能立刻告诉你系统中还有多少隐藏路径。文档建议同时做运行时检查和契约测试，我完全赞成。

## 第二阶段：引入 BoardStabilizer

建立唯一 Core 服务：

```text
BoardStabilizer.ResolveUntilStable(context)
```

它负责：

* 判断当前是否允许补位；
* 寻找可补空位；
* 发牌；
* 执行入场效果；
* 重复直到稳定；
* 检测循环和预算超限；
* 产生完整领域事件。

## 第三阶段：把旧调度器变成空壳调用

暂时保留：

* `DrainRefillScheduler`
* `ResolvePostKillFill`
* `FusionRefillScheduler`

但让它们统一调用 `BoardStabilizer`，而不是分别实现自己的补牌逻辑。

这样可以降低迁移风险。

## 第四阶段：把稳定化移到统一事务边界

确认所有玩家意图最后都会经过：

```text
ResolveConsequences
→ StabilizeBoard
→ CheckNodeCompletion
→ ReturnToInteraction
```

此时旧剧本中的手动 Fill 就可以逐步移除。

## 第五阶段：表现层彻底去规则化

表现层只消费：

* `CardDealt`
* `CardRemoved`
* `BoardRotated`
* `TriggerResolved`
* `BoardStabilized`

不再调用补牌、不再判断击杀后是否应补、不再因为 View 失败修改 Core。

---

# 十一、建议明确写进 ADR 的核心契约

我会把 ADR 的中心句写成下面这样：

> 在允许补位的交互阶段中，一次外部意图只有在其所有派生效果均已结算、盘面已达到稳定状态后才算完成。稳定状态定义为：节点未终止时，盘面不存在可由当前牌堆补充的空位。补位及其派生触发属于 Core 结算；表现层仅负责按 Core 输出的事件序列进行展示，不得决定、取消或补造领域事件。

再增加四条约束：

1. **单一真相**：格位占用只以 Core 为准。
2. **因果可追踪**：每次发牌携带 `Reason`、`TransactionId`、`CauseActionId`。
3. **稳定化可终止**：有 Action Budget、循环检测和明确异常。
4. **表现可重建**：表现层可从 Core Snapshot 完整重建，不反向修正 Core。

---

# 最终结论

你现在遇到的不是“动画层偶尔忘记调用一个函数”，而是**领域规则被错误放进了流程剧本**。

最合适的架构不是：

```text
各种表现剧本决定什么时候补牌
```

而是：

```text
Core 在一次交互结束前自动结算到合法稳定状态
表现层忠实播放这次结算产生的因果事件
```

不过需要特别注意：

> **把规则放进 Core，不等于把补牌塞进任意 Action 的尾部。**

正确的做法是建立一个明确的 Core 稳定化阶段，以“当前意图及全部派生效果已经结算”为边界，补到不动点，然后才重新开放玩家操作。

用一句更工程化的话总结：

> **Core 应拥有补牌的必然性与确定性；表现层应拥有补牌的节奏与可读性。**
