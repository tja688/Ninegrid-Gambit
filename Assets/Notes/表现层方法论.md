## 一、先破案：为什么"前 1~3 张牌瞬间出现在终点"

你描述的症状特别典型：**代码逻辑完美无缺、排查不出、怀疑到 DOTween 内核，但你自己在 DOTween Timeline 里预览又完全正常。** 这几乎可以锁定一个原因——**不是逻辑 bug，是"首帧 deltaTime 尖峰"吃掉了开头几个 tween**。

机理是这样的：

- 你的 DOTween Timeline 在运行时本质就是一条 `DOTween.Sequence()`（这一点 `table-nine-performance-crafting` skill 的 `references/dotween-timeline-route.md` 里已经考证过了），靠每个 clip 的 `delay` 错开时序。
- DOTween 的 Sequence 默认用 `Time.deltaTime` 推进。**它不会 clamp 首帧的超大 delta。**
- 在游戏里，AI 写的脚本通常是**同一帧里**：实例化/激活 20 张卡 → `GetComponent` → 建一条大 Sequence → 立刻播放。实例化 20 个对象本身很贵，于是**播放开始的那一帧 deltaTime 异常巨大**（可能 0.1~0.3 秒）。
- Sequence 第一次 `Update` 就直接快进了这 0.1~0.3 秒。凡是 `delay` 落在这个窗口里的前 1~3 个 tween，**直接被判定为"已经播完"**，于是瞬移到终点。后面的牌因为 delay 更大，逃过了首帧，所以正常。

**为什么你自己 Timeline 预览永远正常**：编辑器里点预览时，场景早就 warm 好了，没有"同帧实例化 20 个对象"的开销，首帧 delta 是正常的 16ms，自然一张都不会被吃。**这就是"同一份编排，你能复现、AI 不能"的真正原因——差别不在代码，在运行时上下文（冷启动 vs 热预览）。**

这也解释了为什么你怎么查代码都查不出：因为代码真的没错。

破解办法（任选，建议前两个一起上）：

1. **生成对象和启动 Sequence 分两帧**。先实例化/布置好所有卡（这一帧很贵无所谓），`yield return null` 等一帧，**下一帧再 `sequence.Play()`**。这样启动帧的 delta 是正常的，开头几张不会被吃。这是最稳的根治。
2. 全局开 `DOTween.useSmoothDeltaTime = true`（用 `Time.smoothDeltaTime` 推进，自动平滑尖峰），并设 `DOTween.maxSmoothUnscaledTime`。这是兜底。
3. 建 Sequence 时先 `.Pause()`，所有 tween 加完后再 `.Restart()`/`.Play()`，避免"边建边被推进"。

> 记住这条经验：**只要你看到"开头几个元素瞬移、越靠后越正常"，第一反应永远是首帧 delta 尖峰，而不是去逐行查逻辑。** 这是 DOTween 在"重对象生成 + 同帧播放"场景下的头号坑。

## 二、核心方法论：把表现层拆成"四个盒子"

你现在痛苦的根源，是脑子里只有两个概念——"卡牌对象"和"DOTween 编排"——然后让这两个直接互相纠缠。一旦要联动（发牌+补位），这两个概念就互相撕扯，于是你开始纠结"切子对象还是改位置""要不要做区域检测"。

正确的拆法是 **4 个盒子，各司其职，互不知道对方内部**：

| 盒子 | 是什么 | 关键纪律 |
|:--|:--|:--|
| **① 锚点 Anchor** | 场上一堆**永远不动**的空 Transform：牌堆位、9 宫格 9 个槽、手牌位、弃牌位。按 `SlotId`/`ZoneId` 解析。 | 锚点是"舞台地标"，只提供坐标，**自己永不动、永不参与动画**。 |
| **② 演员 Actor** | 一个绑定 `CardUid` 的卡牌视图（从对象池取）。它是"提线木偶"，对动画**没有任何意见**。 | 演员**全部挂在同一个扁平父节点下**（一个 ActorLayer），**绝不 reparent 到槽位底下**。"它在哪个区域"是数据，不是层级。 |
| **③ 表演 Performance** | 你手搓烘焙出来的**纯 DOTween 黑盒**，参数化：`PlayDeal(from, to, index, total)`、`PlayShuffleIn(...)`、`PlayRotate(angle)`。不认识 uid、不认识内核。 | 一份切片 → 沿参数推广（`table-nine-performance-crafting` skill 讲的就是这件事）。可打断、可重入。 |
| **④ 导演 Director / 适配器** | 唯一同时认识"内核"和"演员"的人。消费 `PresentationBatch`，按 `Sequence` 走指令，用 `CardUid` 找演员、`SlotId` 找锚点，调表演；同 `ActionId` 的并行；批末发 `PresentationFinishedCommand`，再用 `CoreViewSnapshot` 把所有演员对齐到权威终态。 | 它只做"翻译和调度"，**不含任何游戏逻辑，也不含任何手感**。 |

这套拆法直接解决你纠结的所有问题，因为每个纠结都只属于某一个盒子，不会再互相打架。你那三个 skill（`table-nine-performance-crafting` = 盒子③、`table-nine-interaction-crafting` = 泳道 B 交互 FSM + 本地反馈、`table-nine-adapter-crafting` = 盒子④）已经覆盖表演/交互/回放三条线，但你没把"②演员对象管理"和"①锚点"这两层显式拎出来，所以做联动时它们就糊在一起了。

## 三、用四个盒子，逐个拆你的痛点

### 痛点 1：到底"切子对象"还是"改位置"？→ 都不要，**别 reparent**

这是你最大的认知陷阱。**为动画而 reparent（把卡塞进槽位子节点 / 切到另一个父对象）是 90% 痛苦的来源**：换父节点会导致世界/本地坐标跳变、SortingGroup 重算、正在跑的 tween 目标失效。

正确做法：**所有演员永远待在同一个扁平 ActorLayer 里，从头到尾不换爹。**"这张卡现在属于牌堆 / 属于格6 / 在手牌"——这是**数据**（演员身上记一个 `currentAnchor`），不是层级关系。卡从牌堆到格6，就是"演员从锚点A tween 到锚点B"，仅此而已。显示层级用 sorting order 数据驱动（你那个 `TableNineCardDeckAdaptor` 已经在干这事了，思路是对的，只是它现在还绑在"靠子物体顺序"上，应该升级成"靠数据 order"）。

> 一句话：**位置是数据，不是父子关系。** 把这条刻进去，"切对象还是改位置"这个问题本身就消失了。

### 痛点 2：发牌后"补位"怎么做？→ **绝对不要做区域检测**

你现在想"卡脱离区域就触发补位"，然后立刻自己发现了它的致命问题：连发 8 张时第一张触发了、后面还在飞，补位算不清、会抖。**这个方向是死路，请彻底放弃。** 区域检测是"用物理现象去反推逻辑"，天然有竞态和抖动。

正确的心智是反过来的：**补位不是"牌飞走"这个物理动作的后果，而是"牌堆里少了牌"这个数据事实的后果。** 而这个事实，你的内核**已经算好、而且已经防抖合并好了**——架构文档第 8.1 节白纸黑字写着 `FillEmptySlotsAction` 内部"合并短时多次请求，单次批量结算"，而且内核会发 `SlotsFilled` 事件（我在 `PresentationEventMap` 里看到了：`CoreEventType.SlotsFilled → FillSlots`，`Amount` 字段就是补了几张）。

所以补位的正确实现是 **"声明式重布局"**：

1. 写一个纯函数 `DeckLayout(n)`：给定牌堆里**当前还剩 n 张牌**，返回每张牌**应该在的标准位置**（堆叠的扇形/错位坐标）。
2. **任何时候牌堆内容变化**（发牌走了几张、补进来几张），导演就重新算一遍 `DeckLayout(newN)`，让**所有还在牌堆里的演员一起 tween 到自己的新标准位**。

这一下解决了你所有顾虑：

- "连发 8 张会不会抖" → 不会。内核已经把这 8 次合并成一次结算，你只会收到**一个**最终的"牌堆现在剩 N 张"的结果，重布局一次到位。
- "联动补位动画怎么做" → 它**自动就是联动的**：所有剩余卡同时滑向新位置，就是你想要的那种"牌堆塌缩补位"的连贯动画，你一行特判都不用写。
- 就算某帧真的来了连续两次变化，DOTween 的可打断特性（`Kill` 旧 tween + 从**当前位置**重新 tween 到新目标）会让它平滑过渡，而不是跳变。

```csharp
// 盒子④导演里的"重布局"骨架（示意，非最终代码）
void RelayoutDeck(IReadOnlyList<int> deckCardUids) {
    int n = deckCardUids.Count;
    for (int i = 0; i < n; i++) {
        Actor a = actors.Resolve(deckCardUids[i]);
        Vector3 target = DeckLayout(i, n);   // 纯函数：第 i 张、共 n 张该在哪
        a.PlayMoveTo(target);                // 盒子③表演：从当前位置平滑滑过去
    }
}
```

### 痛点 3："写死 20 张 + 只喂 13 张代理"的笨办法 → 换成"一份切片 × N"

你那个"做死 20 张、真实只喂 13 张、后 7 张空演"的方案，能还原效果，但你自己也说了，一旦要联动就难受。它难受的根因是：**你把"20 张入场"当成了一个不可分割的固定整体去复刻。**

而你的 `table-nine-performance-crafting` skill 第 3 条铁律恰恰就是治这个的：**"沿参数推广，别按个例写死。"**

正确做法：你**只手搓"一张牌入场"这一份切片**（一个代表性的运动曲线/手感），让 AI 把这**一份**烘焙成参数化黑盒 `PlayDeckEnter(index, total, fromAnchor, toAnchor)`。然后导演**循环真实的 N 张牌**，用错开的 delay 调 N 次。13 张就调 13 次，20 张就调 20 次，**永远精确匹配真实数量**，没有空演、没有冗余。

而且——这正好顺手解决了第一节那个"前几张瞬移"的 bug：**当 stagger（错峰延迟）是你在代码里自己控制的，你就可以把整批 Play 推迟一帧再启动**，首帧尖峰再也吃不到你的牌。

> 你之前让 AI 复刻"整条 20 对象 timeline"失败，是因为那是个**又大又冷启动又多对象**的任务，正好踩满所有坑。改成"复刻一张牌的一份切片"，任务瞬间变小、可单测、可对照预览——这才是 AI 能稳定做对的粒度。

## 四、把开局全流程用四个盒子串一遍（你会发现它变简单了）

你描述的"卡入牌堆 → 牌堆铺开 → 发 8 张到格 → 后续逐张补位"，对应到内核事件流是这样的，每一步都只落在某一个盒子里：

| 玩法步骤 | 内核事件 | 谁来演 | 怎么演 |
|:--|:--|:--|:--|
| 卡全部进牌堆 | `CardSpawned`/`ContentLoaded` | 导演 | 取 N 个演员绑 uid，调 `PlayShuffleIn` 飞进牌堆锚点 |
| 牌堆铺开 | （同上批，或单独阶段） | 导演 | 调一次 `RelayoutDeck`，所有演员滑到 `DeckLayout(N)` 标准位 |
| 发 8 张到格 | `CardDealt`(每张带 `FromSlot`/`ToSlot`/`CardUid`) | 导演 | 按 `ActionId` 分组并行，对每张调 `PlayDeal(deckAnchor→slotAnchor, i, 8)` |
| 牌堆补位 | `SlotsFilled`(`Amount`) | 导演 | 发完后用最新牌堆列表再调一次 `RelayoutDeck`，自动联动塌缩 |
| 进入对战旋转/撞击/消失 | `BoardRotated`/`DamageDealt`/`CardRemoved` | 导演 | 各调对应表演黑盒；批末 `PresentationFinishedCommand` + 快照对齐 |

你看，**整个流程里"对象管理"只有一件事：从池里取演员、绑 uid、记它当前锚点。没有任何 reparent、没有任何区域检测。** 所有"联动"都退化成"重新跑一次布局函数 + 大家一起 tween"。复杂度被摊平了。

兜底很重要：每批播完，用 `CoreViewSnapshot`（里面有 9 个槽的权威 `CardUid`/位置）把所有演员**强制 snap 到权威终态**。这样即使你跳过某段动画、或动画被打断，最终画面永远和内核一致——这正是你"可选择性消费"的底气所在。

## 五、回答你最担心的：以后做"我自己都搓不出的乱飞曲线 + 随机"怎么办？

这恰恰是**纯代码表演比 Timeline 更强**的地方，一旦你接受"Timeline 只是 authoring/预览工具、运行时可抛弃"，这个恐惧就反转成优势：

- **乱飞曲线** → `DOPath`（传一组控制点）或采样一条 `AnimationCurve` 当路径，方向用你 skill 里的 **Rig 容器法**（整段表演在父节点本地空间搓一份，播放前把 Rig 旋到任意角度/镜像）覆盖任意方向，不写死 N。
- **带随机的运动** → 把**种子**当参数传进表演黑盒。这样"随机乱飞"是**确定性、可复现、可单测**的——和你内核"带种子 RNG"的哲学完全一致。你甚至可以让内核把种子塞进事件，表现层照着演，回放/截图测试都成立。
- 你**不需要手搓出最终那个炫酷大场面**。你只手搓"一条代表性轨迹的手感"，剩下的数量、方向、随机分布全是代码沿参数推广。这就是你那条 skill 的全部威力，你只是还没在"复杂效果"上用它而已。

## 总结：你要补的三块拼图

1. **认知**：表现层不是"卡牌 + DOTween"两件事，是**锚点 / 演员 / 表演 / 导演**四件事。你的痛苦全部来自把②③④糊在一起。
2. **两条铁律**：①**为动画绝不 reparent，位置是数据**；②**补位/联动绝不做区域检测，而是"数据变了 → 重跑布局函数 → 大家一起 tween"**（内核已替你防抖）。
3. **AI 协作粒度**：别让 AI 复刻"整条多对象 timeline"，让它烘焙"一份切片 → 参数化黑盒"，导演循环真实 N 个驱动它；并且**重对象生成后推迟一帧再启动 Sequence**，根治"前几张瞬移"。
