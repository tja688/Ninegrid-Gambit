# 灵动 UI：内容组织探查与落地判断

## 一句话结论

**不必把「参考」大盘里的面板搬进运行时载体，也不必按「1 号面板永远装 1 号内容」去重绑父子。**  
面板编号复用的是**几何身份（载体）**；美术落在各构型里的 Text Overlay / Anchors 是**构型样板侧的功能面配方**，应被烘焙成「内容槽 ↔ 载体 ID ↔ 显隐/策略」数据，驱动**唯一一套运行时内容舞台**。  
当前最大的错位是：布局系统已经只驱动构型 0 的 12 块背板，但文字仍绑在各失活样板内部的同名面板上——内容与载体脱节。

## 1. 现状探查（UITestSence）

### 1.1 布局运行时（已落地、符合 Spec）

| 项 | 现状 |
|----|------|
| 固定载体 | 仅 `大盘构型0-主菜单` 下的 `1..12`（`SpriteRenderer`）被 `LivingUiSceneLayoutSource` 当作运行时载体 |
| 其它构型根 | Capture 后 `SetActive(false)`，只作**终态快照样板**（位置 / size / sorting） |
| Director | 转场只改载体 pos + `SpriteRenderer.size`，不 `SetParent` |
| 内容系统 | LivingUI 程序集内**尚无** ContentSlot / ContentChoreographer / 功能面策略 |

这与 Spec「构型样板烘焙 → 唯一运行时载体集」一致；核心布局切片刻意不碰文字槽。

### 1.2 美术内容落点（每构型一份「完整页」）

每个大盘根结构几乎同构：

```text
大盘构型X
├─ Text Overlay UI     // TMP 文案（多数默认失活）
├─ Anchors             // 世界侧图标/槽位占位（多数默认失活）
└─ 1..12               // 纯底板 SpriteRenderer，无子内容
```

| 构型 | Text 约 | Anchors 特点 |
|------|---------|--------------|
| 0 主菜单 | 5（标题/开始/设置/结束/版本） | 几乎空 |
| 1 人物选择 | 4 | 头像/选项/属性图标 |
| 2 核心战斗 | Notice / Level / InGameInfo… | 完整：手牌、场地、卡组、遗物、技能、玩家信息 |
| 2-1 奖励 | Notice + 属性 + 跳过 | 精简玩家信息 |
| 2-2 卡组 | Card Info + PlayerInfo | 卡组槽 + 遗物/技能（无 Ground/Hand） |
| 3 房间 | Level + InGameInfo | 类似战斗但无 Ground/Hand |
| 4 路线 | Overlay 空；Binder 有 8 条 **text=null** | Anchors 空 |

**关键事实：底板 `1..12` 下没有任何内容子物体。**  
内容从未挂在「面板子节点」上，而是挂在同构型的 Overlay / Anchors 兄弟树上——这其实更接近 Spec 的双渲染域，只是被「每构型一整页 Prefab」的作者习惯包了一层。

### 1.3 LivingText 绑定（前置落地的副作用）

七套 `LivingTextWorldBinder` 均绑定到**本构型内部**的 `大盘构型X/N`，例如：

- 主菜单：标题→`0/4`，开始→`0/12`，设置→`0/11`，结束→`0/2`
- 战斗：Hp→`2/6`，Name→`2/4`，Armor→`2/12`…
- 卡组视图：Hp→`2-2/12`，Gold→`2-2/5`…（与战斗的载体 ID **不一致**）

Play 时样板根失活 → Overlay 不在层级中生效 → 绑定目标也不是运行时载体。  
因此：**换域 + 跟随背板在「独占激活某构型」的编辑 SOP 下成立，但接不上 LivingUI 的单载体运行时。**

另：构型 0 的 `Text Overlay UI` 当前 `activeSelf=false`，演示布局时主菜单字也默认不显示。

### 1.4 同号面板 ≠ 同功能面

跨构型尺寸差异很大（载体在变形，不是换页）：

| 载体 | 主菜单 | 战斗 | 卡组视图 | 房间 | 说明 |
|------|--------|------|----------|------|------|
| P3 | 3.1×3.4 | **6.8×7.4** | 3.3×2.6 | 6.8×4.8 | 主舞台板 |
| P4 | **9.9×7.0** | 3.0×2.0 | 4.0×2.0 | 3.0×2.0 | 主菜单大标题板 ↔ 局内姓名小板 |
| P8 | 3.0×1.0 | 3.0×1.0 | 2.1×1.0 | **10.4×1.0** | 房间变成长条 |
| P12 | 3.3×2.0 | 3.0×2.5 | **10.0×5.4** | 3.0×2.5 | 卡组视图主展示面 |

同一语义文案绑到的载体 ID 也随构型变：

| 语义 | 战斗 | 卡组 2-2 | 房间 | 奖励 2-1 |
|------|------|----------|------|----------|
| HpText | 6 | **12** | 6 | 6 |
| GoldText | 8 | **5** | **10** | 8 |
| ArmorText | 12 | 12 | 12 | **7** |

→ **「1 号永远是 1 号」只保证载体身份；功能面与内容槽必须按大盘构型声明映射，不能假设内容永远住在固定编号下。**

跨构型重复出现的 TMP 名（至少）：`HpText` / `AttackText` / `ArmorText` / `GoldText` / `Card Info Text` / `NameText` —— 说明美术在复制「局内 HUD」，而不是在维护单一内容实例。

## 2. 与设计思想的对齐

### Spec 已定边界

1. **权威在大盘构型终态**，运行时只驱动一套固定身份载体。  
2. **世界背板 vs 屏幕文字**分域；默认文字走内容槽，不逐帧追背板。  
3. 内容策略主干：`HideDuringTransit` / `FixedSlotSwap`（及方案文档扩展的 BoundaryReveal / Travel / Dock）。  
4. 构型样板 = 人与 AI 观察 + **烘焙数据源**，不是七套并行运行时 UI。

### 内容管理方案（Content Choreographer）补的是哪一层

布局切片已证明：`TransitionPlan` → 载体投影。  
内容方案要求：同一份 Plan 再投影出 Clip / Density / Travel —— **内容是面板时空轨迹的第二投影，不是第二套布局权威。**

当前缺口正好是：

```text
已有：Intent → Director → Planner → Player → WorldCarrierProjection
缺失：                         ↘ ContentChoreographer → ContentProjection
```

`LivingTextWorldBinder` 的 LateUpdate 追 Transform，是临时视觉桥，**与「固定槽 + 裁剪窗 / 同 Plan 采样」目标冲突**；可作为过渡期验收工具，不应成为内容权威。

## 3. 核心判断：大改层级，还是复用？

### 3.1 面板载体 —— 已复用，勿搬

- **不要**把构型 1..4 的 `1..12` 合并进构型 0。  
- 样板底板继续只贡献终端 Rect；身份集合校验已在 `LivingUiSceneLayoutSource` 里。

### 3.2 文字 —— 复用语义实例，不复用「七套 Overlay 树」

| 做法 | 建议 |
|------|------|
| 把各样板 TMP 全部 Move 到构型 0 面板子节点下 | **不建议**（破坏双域、尺寸用 size 变形时子节点语义混乱） |
| 保留七套 Overlay，运行时轮流 SetActive 样板根 | **不建议**（与单载体权威打架，转场无法统一编舞） |
| **一套运行时 ContentStage + 按构型烘焙的槽配方** | **建议主路径** |
| 样板 Overlay 继续留在各构型下作作者参考 / 烘焙源 | **保留** |

重复 HUD（血攻防金、卡牌信息）应收敛为**少量 ContentFace 实例**（或带 Full/Compact 变体），由构型许可表决定显隐与挂靠载体；不要 2/2-2/3 各留一份互相追不同背板。

### 3.3 Anchors（世界图标/槽）—— 分两类

| 类型 | 例子 | 建议 |
|------|------|------|
| 跨构型长存 HUD 图标 | 血/攻/防/金、头像、设置钮 | 运行时单一 WorldContent 组；位置由「相对载体 ID 的偏移」烘焙；策略偏 `TravelWithCarrier` 或 `TravelThenDock` |
| 构型专属 / 场地 | `GroundAnchors`、`CardHandAnchors`、卡组 slot 网格 | 属**受保护场地或场地覆层**语义，不宜塞进 12 载体子树；用构型许可 + 覆层/场地系统显隐，Anchors 作烘焙点位 |
| 仅装饰 | 部分 Outlook | `HideDuringTransit` 或随构型开关 |

美术 Anchors 与底板同级、绝对摆位 —— 烘焙时应记成「相对某载体终态中心的局部偏移」，而不是运行时继续依赖失活样板 Transform。

### 3.4 对「面板编号固定」的正确用法

```text
CarrierId (1..12)     = 几何身份，跨构型变形
FunctionalFaceId      = 这一刻这块板在演什么戏（玩家信息 / 卡组入口 / 标题…）
ContentSlotId         = 屏幕文字槽身份（可固定，不随载体飞）
ContentInstance       = 真实 TMP/图标实例（尽量单例或少量变体）
LayoutBlueprint       = 某大盘下：Face→Carrier、Slot→配方、许可变体、内容策略
```

所以：**编号固定支持「同一块板变形」；不支持「内容永远挂在 N 号下不用改映射」。**  
卡组视图里 Hp 绑 12、战斗里绑 6，在产品上可以是合法的 Face 换板，但必须写进蓝图，而不是靠七套场景树碰巧摆对。

## 4. 建议的内容组织（落地骨架）

### 4.1 运行时层级（概念）

```text
LivingUiStage
├─ Carriers (现有 构型0 / 1..12)          // 只动背板
├─ WorldContentStage                       // 图标等世界内容（可选分组）
│   └─ Face groups（PlayerHudIcons, …）
└─ TextContentStage (独立 Canvas / UICamera)
    └─ ContentSlots（固定槽 + 少量 Travel 槽）
        ├─ Slot_Title / Slot_PlayerStats / …
        └─ 每槽：Full / Compact 预排版变体（密度阶梯）
```

样板根保持失活；**不再**作为 Play 时内容父级。

### 4.2 数据：从样板「收割」而不是「搬家」

对每个大盘构型烘焙（可先半自动）：

```text
LayoutContentRecipe[layoutId]
  - faces[]: { faceId, carrierId, policy, densityLadder, worldAnchorOffsets[] }
  - slots[]: { slotId, faceId?, canvasRect/authoredOffset, variantIds, revealProfile }
  - visibility: 哪些 face/slot 在该构型默认 Visible / Concealed
```

收割源：

1. 现有 `LivingTextWorldBinder` 的 text→panel 映射 → 改写成 `slot → carrierId`（目标改为**运行时载体**，不是样板路径）。  
2. Anchors 相对最近/指定面板的偏移 → `worldAnchorOffsets`。  
3. 人工校对：AI 绑错、同字绑多板、构型 4 空 text 等。

### 4.3 显隐与转场（接 Content Choreographer）

- **权威时间源**：只认当前 `TransitionPlan`（含 generation）。  
- **默认**：非随行文字 `FixedSlotBoundaryReveal` —— TMP 不动，用面板投影 ∩ 槽矩形做 Clip；密度 Full→Compact→Identity→Concealed + 迟滞。  
- **跨构型仍显示的 HUD**：优先 `TravelThenDockToSlot` 或 Face 换板时的 SemanticSwap，避免整页 SetActive。  
- **构型专属大段文案**（主菜单标题 vs 人物介绍）：`FixedSlotSemanticSwap` 在构型标记点换文案/换变体，而不是换整棵 Overlay。  
- **HideDuringTransit**：装饰与即将被完全替换的块。

第一刀仍建议方案文档里的窄案例（单信息面 + 右边界收缩 + Clip），但绑定目标必须是**运行时载体 Rect 采样**，不是样板 `Transform`。

### 4.4 与 Selective Look 的关系

- UICamera / NoPixelSnap / Rig 同步：**保留**，挂在**唯一** TextContentStage Canvas 上即可。  
- `LivingTextWorldBinder`：可保留为「编辑器核对相对偏移」的工具；运行时路径应逐步换成 Plan 采样投影，避免双时间源。

### 4.5 明确不做什么（本阶段）

- 不把手改 `.unity` 把七套内容 Merge 进构型 0。  
- 不把 TMP 设为载体子节点靠父子继承位移。  
- 不让七套样板根在 Play 中轮流激活来「显示内容」。  
- 不把 `GroundAnchors` / 手牌强行塞进 LivingUI 载体子树（场地边界仍归受保护场地）。

## 5. 推荐落地顺序（内容侧）

1. **盘点表**（人审）：每个构型 × 每条文案/锚点 → 语义 FaceId、是否跨构型复用、策略初值、载体 ID。重点标出战斗/房间/卡组重复 HUD。  
2. **建 TextContentStage**：合并一套 Canvas；从样板**复制**（非 Move）权威 TMP 到槽位；样板 Overlay 保留参考。  
3. **蓝图配方 v0**：只含 `layoutId → slot 显隐 + carrierId + 静态偏移`；构型切换时 Swap/显隐，暂不做 Clip 编舞。  
4. **重绑**：所有运行时跟随/投影指向构型 0 载体；删掉或禁用样板内 Binder 的 Play 路径。  
5. **ContentChoreographer 第一刀**：单 Face Clip + 密度；与 Plan generation 对齐。  
6. **WorldContent**：先做跨构型 PlayerHud 图标；场地类 Anchors 只烘焙点位，显隐交给场地/覆层许可。

## 6. 待你确认的问题

1. **载体语义是否要产品化？**  
   例如约定「P5/6/7 永远是小属性条」——现在尺寸跨构型稳定，但文案挂靠并不稳定。若产品上**不**保证稳定 Face，则蓝图映射必须每构型显式配置（推荐接受这个现实）。

2. **局内 HUD（血攻防金/姓名）跨战斗、房间、卡组、奖励：要一份长存实例，还是允许各构型语义变体？**  
   长存更贴 Travel/Dock；若奖励页版式差很多，可用同一 Face 的 Compact 变体，而不是第四套 TMP。

3. **Anchors 里的 CardDeck / Relic / Skill：是正式可交互运行时槽，还是纯构图参考？**  
   若是正式槽，内容舞台要接现有 `ContentIconSlotHitProxy` 等，而不是只做视觉跟随。

4. **构型 4 路线**：Overlay 空、Binder 空引用——是未做完，还是刻意无字？影响配方是否为空构型。

5. **主菜单 Overlay 默认失活**：演示布局时是否应自动打开当前构型对应内容配方？还是内容演示另键触发？

6. **AI 已写的跨样板绑定**：是否承认「几何绑定表可作烘焙草稿」，以人审校正后的表为准，而不是继续维护七套 Binder？

## 7. 探查摘要（给协作方）

| 问题 | 判断 |
|------|------|
| 参考构型里的内容没用上？ | 对。运行时只激活载体几何；Text/Anchors 仍困在失活样板里。 |
| 要把参考面板搬过来吗？ | **不用搬面板。** 要收割内容配方 + 建单一内容舞台。 |
| 1 号永远 1 号能否直接复用内容？ | **只能复用载体。** 内容挂靠随构型变，必须蓝图声明。 |
| Selective Look 绑定错了吗？ | 在「单构型编辑验收」下合理；相对 LivingUI 运行时则绑错了域（样板 vs 载体）。 |
| 下一步最小正确步？ | 内容实例收敛 + 配方指向运行时载体；再上 Choreographer，而不是继续给每个样板加 Binder。 |
