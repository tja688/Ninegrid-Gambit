# 策划设计大规模 Core 用例测试可行性报告（2026-06-20）

## 结论

**可行，而且当前项目已经具备大规模 Core 用例测试的主要地基。**

原因很直接：Core 已经是纯逻辑程序集，所有玩家意图有 Command 面，所有状态变化有 GameAction 流水线，所有事实有 EventLog，随机源可种子复现，内容通过 DSL/Catalog/Luban 校验，测试侧已有 ReplayFixture、HeadlessCampaignDriver、HeadlessBatchRunner、InvariantChecker 和 transcript 输出。

建议不要把“大规模用例测试”做成一堆手写 NUnit 断言的堆积，而是分成三层：

1. **策划效果用例**：一条效果一个最小场景，验证 DSL 能否表达和触发。
2. **组合流程用例**：若干效果/卡/房间按真实 Command 串起来，验证事件链、阶段、奖励和生命周期。
3. **无头批量压测**：大量 seed + forced cards + invariants，验证长流程不死锁、不残留、不数值爆炸。

## 推荐测试分层

### Tier 0：架构护栏

每次提交必跑：

- Core asmdef 必须 `noEngineReferences: true`
- Core 不引用 `UnityEngine`
- Systems 不绕过 ActionPipeline 直接改模型
- 所有 CoreEventType 都有 PresentationEventMap

当前已有：

- `Assets/Notes/CI/check-core-guards.ps1`
- `P0ArchitectureGuardTests`
- `P7PresentationContractTests.EveryCoreEventHasPresentationMapping`

### Tier 1：DSL / Catalog 加载期验收

每次新增或修改策划效果必跑：

- effect JSON 可 parse
- `EffectValidator.Validate()` 通过
- atom 已注册
- required/range/schema 校验通过
- content ref 不缺失
- Luban catalog 与 hardcoded/default catalog 一致

当前已有：

- `ContentSystem.ValidateCatalog()`
- `P5EffectSystemTests.AtomRegistryDiscoversCoreP5AtomsAndValidatorReportsFiveDefenseIssues`
- `P6ContentLandingTests.DefaultCatalogValidatesImplementedDslAndTracksLongTailAtoms`
- `P6LubanContentTests.GeneratedLubanTablesCanFeedContentSystem`

### Tier 2：单效果最小场景

目标：验证一条策划效果在最小棋盘下正确触发。

推荐断言：

- 初始棋盘/属性/道具槽符合用例
- 发送真实 Command 或执行单个 Action
- EventLog 出现关键事件
- 关键 payload 正确：`CardUid`、`TargetUid`、`Amount`、`Delta`、`RemainingHp/Armor`、`SourceDefId/Cause`
- 最终 Model/Snapshot 正确
- owner 离场后 effect 不再触发

当前已有大量范例：

- 凤凰羽毛致命伤
- 落石累计护甲损失
- 重新组合头/身
- 废物老虎机 WeightedRandom
- 条件光环离格失效
- 金币盔甲/嘲讽/范围扩大
- 双倍塔重放帮助卡
- 福地/发现弱点/祝福

### Tier 3：组合流程回放

目标：验证多个效果在真实节点流程中组合不冲突。

推荐用 `ReplayFixture` 或新增数据化 fixture：

- bootstrap catalog
- start node options
- command steps
- expected event sequence
- expected final snapshot
- expected no remaining runtime effect

当前已有：

- `P4NodeFlowTests.FullNodeReplayScriptAssertsAllInteractionPaths`
- `P7PresentationContractTests.LocalReplayFixtureRunnerExecutesNodeTailInCoreTests`

### Tier 4：无头真局 smoke

目标：每次大改后跑完整流程，证明不会卡死、死循环、跨节点污染。

当前已有：

- `HeadlessCampaignDriver`
- `RandomAgent`
- `RunTranscriptWriter`
- `HeadlessInvariantChecker`

推荐默认 smoke：

- 小 catalog：稳定通关，验证 27 节点主流程。
- 生产 catalog：允许 Victory/Defeat/Stalled 分类，重点看 invariant、异常和卡死。
- forced cards：指定某效果在某层某节点必出现，验证长流程中的真实交互。

### Tier 5：批量压测 / 平衡观察

目标：批量跑 seed，输出指标供策划看强度和稳定性。

当前已有：

- `HeadlessBatchRunner`
- CSV/JSON 输出
- `ContentSeed` 与 `AgentSeed` 分离

推荐指标：

- outcome：Victory / Defeat / Stalled / CommandRejected / InvariantFailed
- final floor/node/phase
- command count
- resolved action count
- monster kills
- avatar damage
- final hp/armor/coins
- seen enemy defs
- deck selections
- invariant issue count

## 推荐用例规格

建议把策划用例统一写成一个可转 NUnit fixture 的结构。可以先落 Markdown 表，成熟后转 JSON/YAML。

```yaml
id: skill.falling_rocks.cumulative.case01
designSource: Assets/Docs/...
contentIds:
  cards: [monster.stone_guard]
  effects: [skill.falling_rocks.cumulative]
seed:
  content: 1001
  agent: 2001
setup:
  avatar:
    hp: 30
    attack: 2
  board:
    - slot: 5
      card: avatar
    - slot: 2
      card: monster.stone_guard
commands:
  - type: Attack
    slot: 2
expectedEvents:
  - type: ArmorChanged
    card: monster.stone_guard
    deltaLessThan: 0
  - type: CardDealt
    sourceDefId: monster.stone_random
expectedSnapshot:
  phase: InteractionLoop
invariants:
  - noNegativeHpArmor
  - noRuntimeEffectLeakAfterOwnerRemoved
```

### 字段建议

| 字段 | 说明 |
|---|---|
| `id` | 稳定用例 id，建议和 effect/content id 对齐 |
| `designSource` | 对应策划文档或表格来源 |
| `contentIds` | 涉及的 card/effect/skill/relic |
| `seed` | content seed 和 agent seed |
| `setup` | 头像、棋盘、道具槽、遗物/技能、金币等 |
| `commands` | 真实 Command 序列 |
| `expectedEvents` | 关键事件断言，不要求全量事件都写 |
| `expectedSnapshot` | 终态快照断言 |
| `invariants` | 通用不变量开关 |
| `notes` | 策划意图和边界解释 |

## 建议流程

1. **策划效果入库前分类。** 先判定是 Modifier、RuleModifier、Triggered，确认落点唯一。
2. **写 DSL / Luban 行。** 尽量只组合已有 atom；需要新 atom 时先补 atom 单测。
3. **跑 Catalog 校验。** `ContentSystem.ValidateCatalog()` 必须无 issue，pending effects 不应进入生产默认 catalog。
4. **写单效果最小场景。** 每条新效果至少一个 Tier 2 用例。
5. **写组合回放。** 容易连锁、离场、跨节点、随机的效果补 Tier 3。
6. **加入 forced headless。** 对危险效果在无头真局中强制出现，验证长流程。
7. **跑批量 seed。** 对平衡敏感内容跑 N 个 seed，输出 CSV/JSON。
8. **失败 triage。** 用 transcript 和 ActionLogRow 定位到 sequence、action、effect source。
9. **回归固化。** 每次修 bug，把复现 seed 和最小 fixture 固化。

## 风险与规避

### 1. 自然语言设计歧义

同一句策划文本可能对应 Trigger、RuleModifier 或 Modifier。规避方式：每条效果先写“三态分类 + 触发点 + 目标 + 事件断言”，再写 DSL。

### 2. 随机 Agent 低估强度

RandomAgent 能验稳定性，不等于能验平衡。规避方式：增加 GreedyAgent，至少覆盖“优先击杀、优先保命、优先使用强道具”的会玩基线。

### 3. 用例只断最终状态会漏事件链错误

卡牌游戏经常最终数值正确但中间触发顺序错误。规避方式：关键用例必须断 EventLog 关键 sequence / source / cause。

### 4. 表现层目标选择与 Core Command 不一致

当前 `UseItemCommand` 不带 selected cards / option。规避方式：先补 Command，再把表现层和自动用例都统一走该 Command。

### 5. 新 RuleModifier 只注册不消费

只加枚举和 DSL 不够，必须在规则决策点查询。规避方式：每个 RuleModifier 用例必须包含“规则生效点”的行为断言。

## 推荐落地目录

短期不必新建复杂框架，建议：

- `Assets/Scripts/NineGrid.Core.Tests/Fixtures/`：数据化 fixture runner 和 fixture 类型。
- `Assets/Scripts/NineGrid.Core.Tests/Fixtures/Cases/`：策划用例 JSON/YAML 或 C# case builder。
- `Assets/Scripts/NineGrid.Core.Tests/Simulation/`：继续放 headless / batch / agent / transcript。
- `Logs/sim/`：保留本地生成战报，不进版本库或只提交精选样本。
- `Assets/Notes/`：放用例流程说明、批量结果摘要、人工审查报告。

## 最终判断

当前 Core 的测试可行性已经从“能不能做”进入“怎么规模化管理”的阶段。最值得投入的不是再手写更多零散测试，而是把策划用例规格、ReplayFixture、Headless batch、transcript 和 invariants 串成一条稳定流水线。

建议验收口径：

- 新效果：必须有 DSL 校验 + 单效果最小场景。
- 高风险效果：必须有组合回放 + forced headless。
- 大改 Core：必须跑全量 Core Tests + headless smoke。
- 平衡调整：必须跑 batch，并保存 seed 与指标摘要。
