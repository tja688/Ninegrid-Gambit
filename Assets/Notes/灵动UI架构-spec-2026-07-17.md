# TableNine 灵动 UI 舞台 · Spec

> 状态：ready-for-agent · 日期：2026-07-17  
> 来源：CONTEXT.md 领域词汇 + 灵动 UI 架构 Canvas 对齐结论  
> 目标域：非内核 Flow / Presentation 的灵动界面（不改 Core，不使用 QFramework）  
> 主测试 seam（已确认）：`TransitionPlanner`（纯数据）

---

## Problem Statement

局内与流程界面今天仍是「场景摆放 + `SetActive` 壳路由 + 世界精灵与屏幕 TMP 各自为政」。玩家与作者需要的是一块可流动的像素化舞台：有限个手工权威**大盘构型**之间可丝滑转场，Hover 可预演、点击才提交，文字不逐帧追背板，场地可被活性遮盖但不被重排。现有 `UiPanelRouter` 只能显隐，没有**布局构型**权威、没有**转场计划**、没有**碰撞校验对**与**流动下限**，也无法安全声明**场地覆层**下的输入所有权。继续在旧「面板/覆盖层」语言上堆动画，会组合爆炸、追踪漂移、输入穿透，且无法被 EditMode 纯数据验收。

## Solution

引入**灵动 UI 舞台**：以构型样板烘焙出的权威终态为唯一布局真理；运行时只驱动一套固定身份的**面板载体**；从当前实况到目标构型由**动态时空规划器**在时间预算内联合规划位置、宽高与卡农时差；五次 Hermite（及中立有限时长曲线）只负责连续执行与带速度重定向，不临场猜布局。世界视觉层运动背板，屏幕文字层走固定**内容槽**；Hover 走**构型预演**与**稳定触发区**，点击或流程事件提交**已提交构型**；**场地覆层**只做视觉遮盖与输入门禁，底下**受保护场地**继续按真实时间推进。

首个垂直切片证明范式，不先做全套 UI：「Hover 卡组入口」——左侧信息面切为卡组名称/描述，点击后场地覆层展示完整卡组，再点击撤层；约 3–4 个载体、2 个大盘构型、1 个局部变体，并覆盖快速 Hover 改道与输入穿透。

## User Stories

1. As a player, I want the HUD to morph between a small set of recognizable global layouts, so that mode changes feel intentional rather than like separate pages swapping.
2. As a player, I want hovering a deck affordance to preview the deck-oriented layout without committing, so that I can explore without locking myself in.
3. As a player, I want leaving the stable hover zone to restore the last committed layout, so that previews never strand me in a half-state.
4. As a player, I want clicking to commit a layout, so that my intentional mode changes persist until I change them again or flow overrides them.
5. As a player, I want text labels to stay readable at fixed slots instead of jittering after moving panels, so that information remains legible during transitions.
6. As a player, I want panel backs to keep a recognizable non-zero footprint while morphing, so that the UI still feels like flowing layout blocks even when content is hidden.
7. As a player, I want a field cover to hide the board/hand/deck visually while they keep updating underneath, so that returning from an overlay shows the true current battle state.
8. As a player, I want no clicks, hovers, or hand drags to reach the protected field while a field cover owns input, so that overlays cannot accidentally play cards or pick slots.
9. As a player, I want rapid hover retargeting to feel continuous rather than restarting from rest, so that scrubbing across affordances stays silky.
10. As a player, I want impact shakes and punches to settle back without changing the committed layout, so that juice never corrupts composition.
11. As a player, I want visually swallowed companion panels to still feel like one composition without objects being parented away, so that identity of each carrier stays stable.
12. As a player, I want flow-critical screens (rewards, room events, main menu) to forcibly own the global layout, so that gameplay chrome cannot fight the flow shell.
13. As a designer, I want to author a finite set of grand layouts by hand in an authoring stage, so that composition quality is curated rather than algorithmically invented.
14. As a designer, I want baking a layout template into blueprint data that drives the single runtime carrier set, so that what I see in authoring is what runtime targets.
15. As a designer, I want a permission table of which local variants each grand layout may enable, so that hover micro-changes cannot explode into unsupported combinations.
16. As a designer, I want to declare collision check pairs and intentional overlap exclusions, so that planned overlaps are art-directed rather than treated as bugs.
17. As a designer, I want transition intents with time budgets, ideal canons, style tags, and allowed candidate motion families, so that AI or authors can request motion without hard-coding tweens.
18. As a designer, I want failed plans to return conflict witnesses (pair, interval, min gap, tried candidates), so that I can widen budgets, add candidates, or exclude pairs deliberately.
19. As a designer, I want content projection strategies (hide during transit, fixed-slot swap, travel-with-carrier) per functional face, so that text and icons follow product rules instead of default tracking.
20. As a designer, I want travel-with-carrier content to raise the carrier’s size floor by its envelope, so that following content cannot force zero-area cheating.
21. As a designer, I want flow limits that never allow panels to shrink into needles just to dodge collisions, so that “success” still means readable layout flow.
22. As a designer, I want docking berths that create visual merge via clip and border continuity without changing parents, so that swallow compositions stay authorable and safe.
23. As a designer, I want stable hit zones that do not move with preview carriers, so that hover preview cannot self-oscillate.
24. As a designer, I want diagnostics for solve time, compression integral, makespan, replan count, and input ownership, so that quality regressions are measurable.
25. As a programmer, I want a pure-data transition planner as the primary testable seam, so that layout legality can be EditMode-proven without scenes.
26. As a programmer, I want planner outputs to be generation-stamped plans, so that stale callbacks from superseded intents cannot apply.
27. As a programmer, I want the player/executor to only sample validated plans and support velocity-preserving redirects, so that execution never invents layout.
28. As a programmer, I want fixed-identity carrier roots that never reparent at runtime, so that SetParent handoff bugs cannot appear in UI.
29. As a programmer, I want a fixed transform stack (layout frame, impact frame, flip frame, skin/mask) per carrier, so that layout, juice, and flip stay semantically isolated.
30. As a programmer, I want world visual motion and screen text projection as separate domains, so that pixel snap on backs never forces snap on TMP.
31. As a programmer, I want an input arbiter that gates protected-field channels independently of canvas raycasts, so that OnMouse/Collider2D/manager polling cannot pierce covers.
32. As a programmer, I want Living UI modules to live in non-core Flow/Presentation without QFramework and without depending on Cards convergence towers/drivers, so that the field control paradigm stays a black box we only borrow math from.
33. As a programmer, I want neutral finite-duration curve math shared or extracted for both Cards and UI composition, so that C1 redirect behavior is reused without UI coupling to card leases.
34. As a programmer, I want size channels planned so extrema stay inside bounds without runtime clamp that breaks velocity continuity, so that width/height never go negative or hard-stop mid-curve.
35. As a programmer, I want candidate motion programs (Direct, Contract→Move→Expand, Yield→Fill, EdgePortal, …) searched with conflict-driven scheduling, so that planning stays tractable for ~12–20 carriers.
36. As a programmer, I want lexicographic plan scoring (safety & budget first; then added delay, makespan, compression, rare postures, canon deviation), so that “safe but ugly serial” loses to better parallel plans when possible.
37. As a programmer, I want solving only on intent changes, not every frame, so that CPU stays event-driven inside a few-millisecond budget before considering Burst.
38. As a programmer, I want blueprint assets to encode terminal rects, functional faces, sorting, content slots, and permitted variants, so that runtime has one authoritative layout source.
39. As a programmer, I want carrier definition assets for flow floors, size caps, travel policies, and impact envelopes, so that per-carrier constraints are data, not hard-coded.
40. As a programmer, I want transition style assets for budgets, ideal canons, candidate libraries, and cost weights, so that motion personality is tunable without code forks.
41. As a programmer, I want the first vertical slice to exercise dual-domain projection, stable hits, blueprints, planner, cover, and live field boundary together, so that the paradigm is proven before expanding skins.
42. As a programmer, I want UiPanelRouter’s binary shells to be gradually replaced or wrapped by committed/preview configurations rather than remaining the layout authority, so that legacy show/hide stops defining composition.
43. As a QA engineer, I want EditMode tests that assert external planner behavior (terminal hit, no illegal intersection, flow floors, generation drop, scoring order), so that layout regressions fail in CI without Play Mode flakiness.
44. As a QA engineer, I want optional contract tests for continuous rect validation witnesses and input-arbiter blocking channels, so that collision and cover safety have focused seams without scene dependency.
45. As an AI orchestrator, I want a stable intent contract (source live state, target blueprint id, envelopes, budget, check pairs, allowed families), so that agents can request transitions and interpret failure witnesses without reading Unity scenes.

## Implementation Decisions

1. **Domain vocabulary is binding.** New APIs and assets use CONTEXT.md terms（面板载体、功能面、内容槽、布局构型、大盘构型、构型样板、局部变体、构型许可表、碰撞校验对、转场计划、构型预演、已提交构型、稳定触发区、停泊位、视觉吞并、受保护场地、场地覆层、活性遮盖、流动下限、随行内容）. Legacy “panel/overlay/HUD” language is not the authority for new modules.

2. **Module boundary: non-core Flow/Presentation.** Living UI does not modify Core, does not use QFramework, and does not depend on Cards convergence towers, leases, or Cards-namespaced drivers. Only neutral finite-duration scalar curve / rect trajectory math may be shared or extracted for both Cards and UI to compose independently.

3. **Authority model.** Finite hand-authored grand layouts plus permitted local variants. Runtime never invents a free global layout. Authoritative terminals come from baked layout templates; the planner only invents validated *paths* to those terminals.

4. **Runtime state is not a single enum.** Concurrent facets: committed configuration, preview configuration, plan generation, input owner, and an orthogonal impact channel. Priority: flow-forced configuration > click-committed configuration > hover preview; impact never competes for layout authority.

5. **Intent pipeline.** Interaction intent → Living UI director (priority + target configuration + permitted variant) → transition planner (live state → verified plan or failure witness) → transition player (sample plan; redirect with velocity) → dual-domain projection (world carriers + fixed text slots).

6. **Dual render domains.** World visual layer owns pixelated backs, borders, icons, masks, position/size. Screen text layer owns Canvas/TMP fixed content slots; no per-frame tracking of carriers; content swaps or visibility changes at marked moments. Protected field remains owned by existing field systems; Living UI may cover it but must not rearrange or reset it.

7. **Carrier identity forever fixed.** No runtime SetParent. Visual swallow is docking, clipping, and border continuity only. All carriers share one fixed stage parent.

8. **Per-carrier channel stack (prototype-aligned hierarchy).** Decision-rich shape carried from the architecture prototype:

```
CarrierRoot            // fixed identity, never reparent
└─ LayoutFrame         // planner center pose
   └─ ImpactFrame      // additive impact; must return to zero
      └─ FlipFrame     // flip/portal presentation only
         ├─ SlicedSkin
         ├─ Border/Icon
         └─ ClipMask
StableHitZoneRoot      // independent of CarrierRoot; does not follow preview motion
TextOverlay/ContentSlots  // independent projection; no per-frame chase
```

9. **Planner problem statement.** Given stage bounds, authoritative terminals, and a time budget: from each carrier’s current rect and velocity, jointly solve position, size, and start offsets such that every collision check pair has no illegal continuous-time area intersection, while preferring parallelism, ideal canon, and recognizable layout flow.

10. **Geometry & constraints.** State `qᵢ(t)=(x,y,w,h)` axis-aligned. Exact terminal hit to blueprint. Flow floors `w,h ≥ flow mins` (non-zero). Travel-with-carrier content raises size floors by content envelope. Rects stay in stage bounds unless an action explicitly allows exit. Safety margins apply only to declared check pairs; intentional overlaps are author-excluded.

11. **Size channel rule.** Do not Hermite raw width then clamp (creates velocity discontinuities). Candidate quintics must have all extrema inside `[w_min,w_max]` (same for height); if not, replan with longer budget or continuous braking segments. Runtime must not need hard truncation for ordinary plans.

12. **Content strategies.** Default `HideDuringTransit`; primary text path `FixedSlotSwap` at flip-thin or configuration markers; rare `TravelWithCarrier` raises floors.

13. **Solver algorithm (candidate programs + conflict-driven search).** Snapshot live state → generate finite candidate programs per carrier (Direct, Contract→Move→Expand, Yield→Fill, EdgePortal, …) sharing the same terminal → broadphase sweep AABB prune → continuous narrowphase with adaptive subdivision and separation proofs → conflict-driven start-time search near ideal canon → lexicographic ranking → on failure return witnesses. Solving is event-triggered on intent change, not per frame. Target carrier count ~12–20; start with 2–4 ms sync budget and metrics before Burst.

14. **Anti-cheat.** Area compression is a costly yielding action, not an escape hatch. Flow floors + compression integral reject needle solutions as quality failures.

15. **Asset types (logical).** Layout blueprint (terminals, functional faces, slots, sorting, permitted variants); carrier definition (floors, caps, travel policy, impact envelope); transition style (budget, ideal canon, candidate library, weights). Authoring workflow: hand-build template → bake by carrier id → validate → preview/scrub with collision witnesses → rebake.

16. **Field cover contract.** Visual: world opaque/clip cover, no screenshot swap, no replacing field objects. Time: underneath logic and presentation keep advancing; uncover shows live truth. Input: arbiter blocks field hover/click/empty-slot/hand-drag while cover owns those channels; Living UI itself remains interactive. Canvas ray blocking alone is insufficient against OnMouse/Collider2D/manager polling.

17. **Phased delivery gates.**  
    - 0 Math core: neutral bounded-duration curves, bounded size mapping, rect trajectories — exact endpoints, C1 redirect, size never out of bounds.  
    - 1 Single carrier: world carrier + fixed text slot + stable hit + flip — no self-oscillating hover; no text chase drift.  
    - 2 Configuration assets: bake window, blueprints, permission table, single runtime carrier set — template matches runtime terminal; no duplicated authority.  
    - 3 Fixed-path avoidance: Direct candidates, continuous rect validation, start-offset scheduling — parallel when clear; minimal stagger when conflicting.  
    - 4 Dynamic geometry: Contract→Move→Expand, flow floors, redirect replan — fast A→B→C with no overlap, no negative size, no zero-area cheat.  
    - 5 Field cover: deck/settings cover, unified input ownership, live cover — field advances, play inputs never pierce.  
    - 6 Expression: visual swallow, portal replace, impact bus, AI candidate contracts — impact never pollutes terminals; complex transitions diagnosable.

18. **First vertical slice.** Hover deck entry: left player/stage info becomes deck name/description; click opens field cover with full deck; click dismisses. ~3–4 carriers, 2 grand layouts, 1 local variant; includes rapid hover redirect and input-pierce tests.

19. **Legacy coexistence.** Existing binary shell routing and world/screen HUD continue to operate until replaced per slice; new layout authority must not silently fork a second competing composition system. Description/text routing that already targets fixed TMP destinations is the closest legacy analog to content slots and should be adapted rather than duplicated.

20. **AI orchestration I/O.** Input: live source, target blueprint id, envelopes, content policies, budget, ideal canon, style tags, check/exclude pairs, allowed candidate families. Output: verified plan + makespan, min gap, compression integral, added delay, canon deviation, solve metrics; or conflict witness on failure.

## Testing Decisions

### What makes a good test

Only assert **external behavior** of the planner (and optional narrow secondary seams): given live state + intent + blueprints/constraints, the result is either a plan that hits terminals under declared constraints, or a structured failure witness. Do not assert internal search branch ordering, Unity transforms, tween libraries, or scene object names.

### Primary seam (confirmed)

**`TransitionPlanner` (pure data)**  
- Inputs: live carrier rects/velocities, target grand-layout blueprint, transition intent (budget, ideal canon, check pairs, candidate families), permission-table constraints.  
- Outputs: generation-stamped verified transition plan, or failure witness.  
- Environment: EditMode, no Unity scene, no Cards towers.

### Required external behaviors to cover

- Exact terminal hit for all participating carriers within budget when a feasible plan exists.  
- No illegal continuous-time intersection for any collision check pair; intentional exclusions must not be treated as failures.  
- Flow floors and travel-with-carrier envelopes never violated; needle/zero-area “solutions” rejected.  
- Newer intent increments generation; applying or continuing a stale plan is impossible / dropped.  
- Redirect from mid-plan live state can produce a new plan to a new terminal without requiring zero initial velocity.  
- Lexicographic preference observable at the outcome level (e.g., when both safe, lower added-delay / better parallelism beats forced full serial), without locking internal scorer code shape.  
- Failure returns actionable witnesses (pairs, intervals, min gap, attempted candidate families).

### Optional secondary seams (included in Testing Decisions, not replacing the primary)

1. **`ContinuousRectValidator`** — continuous narrowphase / witness quality for rect trajectories (still pure data).  
2. **`UiInputArbiter` contract** — while field cover owns input, protected-field channels report blocked; Living UI channels remain allowed (fakes/mocks, no full scene).

### Modules under test

- Transition planner and its pure validators/scoring as used through the planner façade.  
- Not required in v1 of this spec’s automated suite: director MonoBehaviours, carrier views, transition player sampling, authoring windows (those get manual/slice gates and later thin tests if needed).

### Prior art

- Pure projector/DTO tests in the presentation stack (ordered steps, commitment tags).  
- Pure arbitration tests (lease/constraint outcomes without scenes).  
- Curve/math tests (endpoint exactness, redirect continuity).  
Mirror those styles: synthetic fixtures in, assert plan/witness out.

### Slice acceptance beyond unit tests

Vertical slice “Hover deck entry” must additionally demonstrate dual-domain projection, stable hit non-oscillation, blueprint fidelity, live field cover, and no input pierce—using diagnostics (`solveMs`, `minGap`, `compressionIntegral`, `replanCount`/`staleGenerationDrop`, `inputOwner`/`blockedChannel`) as acceptance telemetry, not as unit-test internals.

## Out of Scope

- Rewriting Core, battle rules, card data, or Luban content pipelines.  
- Replacing the Cards convergence / lease / tower field-control paradigm, or teaching Living UI to drive card transforms.  
- Migrating the whole product onto uGUI / UIToolkit / QFramework UIKit.  
- Free-form runtime layout synthesis, unconstrained panel parenting, or “any hover to any composition.”  
- Full skinning of every flow shell (reward, room event, main menu, etc.) in the first delivery—only the deck-entry vertical slice is in-scope to prove the paradigm.  
- Per-frame AI replanning, mandatory Burst/Jobs in phase 0–4, or automatic understanding of “artistic overlap” without author exclusions.  
- Pausing or snapshot-freezing the protected field as the cover mechanism.  
- Making all text travel with carriers by default.  
- Formal ADR file creation beyond this Notes spec (unless a later change control requests it).  
- Publishing/triage automation details beyond marking this spec ready-for-agent in Notes (GitHub CLI was unavailable in the authoring environment at write time).
