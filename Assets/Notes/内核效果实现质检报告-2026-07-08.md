# 内核效果实现质检报告（2026-07-08）

> 质检目标：对照 `Assets/Docs` 设计案与 `NineGrid.Core` 现有实现，推演"效果原子 + 拼接组合 + 触发路由 + 栈式处理"这套体系**能否实现设计中的目标效果**。
> 方法：通读效果内核（`EffectSystem` / `EffectAtomLibrary` / `TriggerSystem` / `ActionPipelineSystem` / `CoreActions` / `StatSystem`），再从 `TableNineContentCatalog`（141 条已落地效果）中抽样帮助卡 / 遗物 / 玩家技能 / 怪物技能逐条对照设计文案推演运行时行为。

---

## 一、总体结论

- **体系可行性：成立。** 原子 + DSL 拼接 + 触发点路由 + 栈式反应链（LIFO、深度上限 64）的表达力足以覆盖设计中绝大多数效果语义。抽样中瞭望塔、治疗泉、滚石、绑架卡、坠石、惹我试试、灼热观察、嘲讽、金币盔甲等复杂效果的拼接都是正确且优雅的。
- **但存在 5 个系统级缺陷**，其中 3 个会让一批"字面上已实现"的效果在运行时**偏离设计语义**（详见第二节）。这些不是原子表达力问题，而是生命周期管理和数值管线的缺口。
- **当前"测试都通过"不能作为质量依据**：效果相关测试已在清理中全部删除，目录校验入口也没有任何调用方（见 2.5）。

---

## 二、系统级发现（按严重度排序）

### 2.1 【P0】临时修正（UntilEnemyChanges / UntilBattleEnds）从不清理

`StatSystem.ClearModifiersByScope`、`StatBlock.ClearModifiersByScope`、`RuleModifierRegistry.ClearByScope` 均已定义，但**全代码库无任何调用方**。`PhaseSystem` 的战斗结束、换敌、节点切换路径上没有任何作用域清理逻辑。

影响：

- **历战（skill.battle_hardened）**：设计明确"仅对当前敌人有效，换敌人时复原"（`玩家技能.md` L22）。实现每次触发都 `AddModifier(+2 攻击, scope=UntilEnemyChanges)`，且 `StatBlock.AddModifier` 无去重 —— 加成**永久无限叠加**，等于把一个白色技能变成指数级成长引擎。
- **历战怪物（skill.monster_battle_hardened）**：scope=UntilBattleEnds 同样不清理。碰巧怪物卡生命周期短（被移除时效果随 owner 反激活），设计上"本卡攻击+2"也未要求复原，所以**结果侥幸正确，机制是坏的**。任何未来给玩家挂 UntilBattleEnds 修正的效果都会踩中。

建议：在 `PhaseSystem` 战斗结算收尾处调用 `ClearModifiersByScope(UntilBattleEnds)`；在"当前交战敌人变更"处（需要先补一个"当前敌人"追踪，设计案历战词条已隐含此概念）调用 `ClearModifiersByScope(UntilEnemyChanges)`，`RuleModifiers.ClearByScope` 同步。

### 2.2 【P0】无过滤的 OnBattle 触发语义过宽（一场战斗触发两次 + 任意伤害都算 + 不校验 owner 参战）

`DealDamageAction` 的 post 触发点固定包含 `OnBattle`（`CoreActions.cs` L11-20），而 `OnBattleTrigger.Matches` 在不配过滤参数时只要求本次行动产生过 `DamageDealt/ArmorChanged` 事件；`TriggerAtomBase` 和 `EffectSystem.CanTrigger` **都没有"效果 owner 必须参与本次战斗"的隐式校验**。

一次玩家战斗 = 出手 `DealDamageAction` + 反击 `ConditionalDealDamageIfAliveAction`（`PhaseSystem.cs` L122-128），是**两个**伤害行动；飞刀 / 爆弹 / 烈焰 / 刺皮反伤等效果伤害同样走 `DealDamageAction`。因此裸 `{"atom":"OnBattle"}` 的效果：

1. 每场战斗至少触发 2 次（出手 + 反击各一次）；
2. 任何来源的伤害（帮助卡直伤、效果伤害）都会触发；
3. 与 owner 无关的战斗（玩家打别的怪）也会触发。

目录中共 4 条裸 OnBattle（`TableNineContentCatalog.cs` L432 / L508 / L514 / L906）：

| 效果 | 设计原文 | 实际运行时行为 |
|---|---|---|
| `skill.battle_hardened.battle` 历战 | [战斗时] 攻击+2，换敌复原 | 全场任意伤害行动各 +2，叠加不清（与 2.1 复合） |
| `skill.monster_battle_hardened.battle` 历战怪物 | [战斗时] 本卡攻击+2 | 全场任意伤害（包括别的怪挨打、玩家用飞刀）都给本卡 +2 |
| `skill.survival_wisdom.battle` 生存智慧 | [战斗时] 恢复1血、本卡攻击+1 | 同上，任意伤害都回血加攻，一场战斗吃两次 |
| `skill.space_mastery.battle` 空间掌握 | **玩家与本卡战斗后**，旋转一次 | 任意伤害都旋转，一场战斗转两次，飞刀也转 |

对照组：同目录内瞭望塔 / 治疗泉 / 刺皮 / 惹我试试都正确使用了 `"sourceAction":"DealDamage","targetKind":"Monster","maxActionDepth":0` 全套过滤（L228 / L267 / L284 / L850），能把触发精确限定到"玩家顶层出手打怪"一次。**说明这 4 条是遗漏而非约定**，修法就是补齐同款过滤（涉及"本卡"的还需加 `EventFilter targetIs/actorIs Self` 条件）。

### 2.3 【P0】护甲三层模型未落地：modifier 护甲不参与伤害吸收，且当前护甲无节点重置

设计（`01-机制规则/属性.md`）区分**基础护甲 / 有效护甲 / 当前护甲**，当前护甲在节点开始时取有效护甲，战斗中被消耗。

实现里只有一个 `StatId.Armor` base 值：

- `DealDamageAction` 吸收伤害用 `target.Stats.GetBase(StatId.Armor)` 并直接 `SetBase` 扣减（`CoreActions.cs` L62 / L76）；
- 木盾 +1、重盔甲 +1、木套装 +2 等 **StatModifier 形式的护甲（catalog L354 / L393 / L409）只影响快照显示的 effective 值**（`CoreViewSnapshot.cs` L535），完全不参与伤害吸收 —— 这些遗物的护甲词条实际是空词条；
- 全代码库没有"节点开始时重置当前护甲=有效护甲"的动作，玩家 base 护甲被打掉后**跨节点不恢复**；
- `relic.heavy_armor.node_start` 用 `Player.Armor effective ×0.5` 计算补甲再灌回 base —— 在上述模型下每关叠加进 base，行为与设计"补当前护甲"含义不同。

建议：要么落地三层模型（新增 CurrentArmor，节点开始由 effective 初始化，伤害只扣 Current），要么明确降级设计并让伤害吸收读 effective —— 但后者需要处理"被打掉的护甲"如何表示。这是需要设计决策的结构性问题。

### 2.4 【P1】MaxHp 修正形同虚设：治疗与伤害都以 base 为准

`HealAction` 的治疗封顶用 `GetBase(StatId.MaxHp)`（`CoreActions.cs` L203-206），伤害扣的也是 base Hp。因此：

- `relic.vitality_amulet.max_hp`（血量上限+6）、`skill.hard_skin.max_hp`（+10）都是 **Permanent StatModifier**（catalog L371 / L422），只抬高快照显示的上限，**不产生任何可用血量、也不提高治疗封顶**；
- 对照 `ModifyBaseStatAction` 修改 base MaxHp 时会同步补 Hp —— 说明正确路径存在，这两条效果应改用 `ModifyBaseStat`（或 Heal 封顶改读 effective MaxHp）。

### 2.5 【P1】质量护栏已经空转：效果零测试覆盖、目录校验无人调用

- `NineGrid.Core.Tests` 目前**只剩 `CoreCommandShellTests.cs` 一个文件、4 条用例**，且注释明言"只校验 Command 注册表与 Dispatcher 契约，不跑节点/效果集成"。用户提到的"很多测试用例"在清理中已全部移除 —— **141 条效果 JSON 目前没有任何自动化验证**。
- `ContentSystem.ValidateCatalog()`（含 DSL parse + schema 校验 + 引用完整性检查）在运行时、编辑器、测试中**均无调用方**。目录里一条 JSON 笔误只会在游戏进行到该效果激活时抛异常。

建议（低成本高收益）：加回一条 EditMode 测试：`ValidateCatalog()` 断言 `IsValid && PendingEffectIds.Count == 0`，即可把全部 141 条 DSL 的解析/schema/引用错误挡在编辑期。再为 2.1–2.4 各补一条最小集成测试。

## 三、抽样条目结论

### 3.1 推演成立（设计语义可正确达成）的样本

| 条目 | 要点 |
|---|---|
| 瞭望塔（三段效果） | 角格计数 `counterKey` + 第4次自移除、道具格全套 OnBattle 过滤、使用即弃，三段拼接全部正确 |
| 治疗泉（三段效果） | `OnSelfMove requireAdjacentTo:Player` + `CardZone` 区分场上/道具格，正确 |
| 滚石 | 格3触发 + 格6非精英校验（TargetCount 条件）+ 双移除顺序正确 |
| 绑架卡 | `TransferArmor all→Player` + 移除，符合"获得其当前护甲" |
| 偶数仇恨 | 初判有疑虑，复核后**正确**：RuleModifier 的 `LevelParity target:Self` 转成 `LevelParityStatCondition` 后，伤害评估上下文的 Owner 就是受击怪物，奇偶判定作用在目标怪身上，语义吻合 |
| 嘲讽 | `AttackTargetRestriction` 巧用 ownerUid 作为规则值 + 相邻条件，正确 |
| 金币盔甲 | `GoldArmorAbsorb` 规则在 `DealDamageAction` 内正确消耗金币抵扣护甲伤害 |
| 坠石 | `OnCumulative metric:armorLost threshold:10` 累计洗入石人，正确 |
| 惹我试试 | 全套 OnBattle 过滤 + `targetNot:Self` 排除自己挨打的场景，正确 |
| 灼热观察 | `sourcePrefix:"skill."` 精确区分"怪物技能位移"与系统旋转/帮助卡位移，正确 |
| 强硬（格1/4/7） | `EventFilter ArmorChanged targetIs:Self maxDelta:-1` + `Event.Delta` 取负回敬，正确 |
| 军械库 / 塔之子 / 轻松之路 | OnNodeEnd/Start + WeightedRandom/Spawn/OfferRewardChoice，正确 |
| 献身 / 散架 | OnRemove 后置触发在 owner 效果反激活**之前**派发（`ResolveAction` 先 post 触发再跑 follow-up），自移除也能正确出牌 |

### 3.2 有偏差的条目（除系统级问题外）

| 条目 | 偏差 |
|---|---|
| 凤凰羽毛 | 设计"血量上限+8"属性**未实现**（relic 只挂了 fatal 一条效果，catalog L1057）；"恢复50%血量"被写死为 15 点（L388）；另外该治疗会被"渴望"的 RecoveryMultiplier 翻倍，设计需明确是否允许 |
| 龙鳞甲 | 设计属性"基础护甲+1，血量上限+6"**未实现**，只落了"怪物攻击-1"规则（L1056） |
| 暴力卡 | `scope:Once` 的 DamageMultiplier 会被**任何**玩家来源伤害消耗（含飞刀直伤），设计限定的是"战斗伤害"翻倍；需给规则条件补 sourceAction 约束 |
| 历战 / 历战怪物 / 生存智慧 / 空间掌握 | 见 2.1 / 2.2 |
| 重盔甲 | 见 2.3，"补当前护甲"在当前护甲模型下语义走样 |
| 活力护符 / 硬皮 | MaxHp 词条见 2.4 |

### 3.3 覆盖率

- 效果目录：141 条全部标记 Implemented，0 条 Pending（基线快照中的 32 条 pending 已全部落地）。
- **遗物：目录仅注册 19 个，设计文档 58 个词条，覆盖约 1/3**（缺口集中在蓝/金品质）。技能与帮助卡覆盖基本齐全。
- 结论：缺失遗物大多可用现有原子拼出（多为属性词条 + OnKill/OnNode 触发的组合），落地属于工作量问题而非能力问题；但涉及"护甲"词条的遗物应等 2.3 定案后再落。

## 四、修复优先级建议

1. **P0-a**：给 4 条裸 OnBattle 效果补过滤（纯 catalog 改动，半小时级）。
2. **P0-b**：接通 UntilBattleEnds / UntilEnemyChanges 清理（内核改动，需引入"当前敌人"概念）。
3. **P0-c**：护甲模型设计决策 + 落地（结构性，建议单独开任务）。
4. **P1-a**：恢复 `ValidateCatalog` 的 EditMode 门禁测试 + 为上述缺陷补最小回归测试。
5. **P1-b**：MaxHp 词条改 `ModifyBaseStat` 或 Heal 封顶改读 effective。
6. **P2**：凤凰羽毛/龙鳞甲缺失词条、暴力卡消耗条件、遗物覆盖率补齐。
