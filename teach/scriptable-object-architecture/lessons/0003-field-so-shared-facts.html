Field SO：把「当前事实」做成可引用变量

上一课的「运行时参数」再说准一点：作者要的是会话级当前事实（此刻选中谁），并带变化通知——不是配方上的可调参数。

作者说的「SO 当 field」

普通写法：字段挂在 Player 身上，别人要读就得找到 Player。 Field SO 把这个字段提成一份资产： 

[CreateAssetMenu]
class AbilityFieldSO : ScriptableObject {
  AbilityDataSO value;
  event Action<AbilityDataSO> ValueChanged;
  void SetValue(...) { ...; ValueChanged?.Invoke(value); }
  void Clear() => SetValue(null);
}

技能按钮、鼠标范围、Tooltip 都拖同一份 CurrentSelectedAbility.asset。 按钮只 SetValue；指示器只订阅 ValueChanged——彼此不认识。

Field 表达什么： 「当前事实是什么」（现在选中的是火球）。 对比 Event Channel：「发生了一件事」（刚才点了火球按钮）。 两者有时一起用；本课只钉 Field。 （术语： Field SO）

你们项目里的功能等价物

你们几乎不做「CurrentX.asset」，但同样的职责在：

共享当前事实 作者 Field SO NineGrid
谁拥有输入 CurrentInputOwnerField（若做成） PresentationInputStateSystem.CurrentOwner
主线是否忙 MainlineBusyField（若做成） Director → MainlineBusy；门面 PresentationInputGates

// 你们：事实在 System 里，带可观察布尔
class PresentationInputStateSystem {
  BindableProperty<bool> mOpening, mChoiceOverlay, mBoardSelect;
  InputOwner CurrentOwner { get { /* 由上述布尔推导 */ } }
  void ResetGates(...) { /* 显式清会话事实 */ }
}

若你们用 Field SO 重做，会怎样

例如把 CurrentOwner 做成 InputOwnerFieldSO：

  • UI / HitProxy / 教程都能拖同一资产，少写 GetSystem<T>
  • Inspector 里能看见「当前值」（调试友好，Hipple 也强调 editable / debuggable）
  • 但必须保证全项目只引用一份资产；开局/结束必须 Reset
  • 写入者若分散，就和你们故意用 Command 写门禁布尔的纪律打架
和你们 ADR 最冲的点： MainlineBusy / 输入所有权需要单一真相。 Field SO 靠「大家都拖对了同一个 asset」维持单例感——拖错第二份就静默分裂。 CompositionRoot 注册一个 System，则实例唯一性由装配保证，结构测试可护栏。

优点 / 缺点（只比 Field 这一层）

Field SO System + BindableProperty
解耦方式 拖同一 .asset 架构取同一 System
设计师可见性 高（Project 里能点开） 低（要看调试器 / 自定义窗）
唯一真相 靠引用纪律 靠装配单例 + 测试
脏值 / PlayMode 易残留，要 Reset 也要 ResetGates；但资产不会把运行时写回磁盘（若你误序列化 Field 则更惨）
写权限 易变成人人 SetValue 你们用 Command / 窄 API 收口写
