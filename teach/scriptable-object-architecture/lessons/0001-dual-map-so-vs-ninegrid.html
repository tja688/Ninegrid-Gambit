Lesson 0001 · ScriptableObject 玩法

不是「松散 MVC」，是「同一职责、不同接线」

你的直觉抓住了职责拆分；本课只钉死一件事——两边拆的是同一类活，差别在「模块之间怎么连上」。

先纠正半步

「有点像 MVC」之所以似曾相识，是因为两边都在避免 一个 BattleManager 包办输入、规则、状态、表现。 但 MVC 标签帮不上忙：它说不清 Field SO 和 Event Channel 的差别，也说不清你们为什么有 IntentIntake 却几乎不用 Runtime Field.asset。

本课硬钉子： 职责拆分两边都有； SO 玩法多出来的是 资产接线 ——用同一个 .asset 当通信节点。 NineGrid 用的是 CompositionRoot + Command / Query / Event / System。

作者那条链，翻译成你们的话

总结里的主路径是：

场景输入 → Bridge → Rules Model SO → State/Field SO
         → Event Channel → Visual / UI

换成 NineGrid 的生产路径（见 presentation.md）：

HitProxy / 场景 Host → Controller → IntentIntake.Submit
  → Director / Core Command → 事件与 Present Channel → View

输入唯一收口： ADR-0004。 SO 经典胶水源头： Ryan Hipple · Unite 2017。

SO 侧怎么「玩」： Prefab A 与 Prefab B 不互相 GetComponent，而是都拖同一份 CurrentAbility.asset 或 AbilitySelected.asset。 解耦发生在 Project 窗口的引用上。
你们怎么「玩」： PresentationCompositionRoot.Install(bindings) 把 System 与场景 Host 装好；写走 Command，读走 Query，输入必须过 IntentIntake。 解耦发生在接口与装配代码上；结构测试防止回流巨型宿主 / 业务静态 Sink。

常见误判： 「可拖拽、可视化」是资产接线的副产品，不是架构的全部优点。 真正共同优点是：输入 / 规则 / 表现不再堆在一个 Manager 里。 真正分歧是：共享节点放在磁盘资产上，还是放在代码装配出的 System 上。

本课主读

先看 Hipple 讲座前 15 分钟（变量 SO + GameEvent 动机），建立「资产当胶水」的原始画面： Unite 2017 · Game Architecture with Scriptable Objects。 再扫一眼你们的 presentation.md · 装配与读写约定， 确认「胶水」落在 CompositionRoot，而不是 Runtime Field.asset。

有哪一行对照「对上了但说不顺」——直接在对话里追问，我可以对着仓库具体类型拆。 下一课预定：配置 SO——你们已经在用的那一块，先分清「该做成资产的配置」和「不该做成资产的运行时」。
