Lesson 0006 · ScriptableObject 玩法

Bridge：只翻译场景，不判决规则

Bridge 不是 SO——它是挂在场景里的 MonoBehaviour，把点击、动画结束、生命周期翻成「业务请求」。你们把同一缝拆成了 HitProxy + Hook + Controller。

作者的 Bridge 做什么

Bridge 连接两个世界：Unity 场景（Collider、Button、Timeline 信号）与 SO 业务世界（Rules / Field / Event）。 

class UnitSelectionBridge : MonoBehaviour {
  UnityEvent<Unit> onUnitSelected;
  void HandleUnitClicked(Unit unit) => onUnitSelected.Invoke(unit);
}
// Inspector: OnUnitSelected → RulesModel.ApplySelectedUnit
纪律： Bridge 可以拿 Camera / Collider / GameObject； 不应该内嵌「是否友方、是否已行动」这类规则。 判决交给 Rules Model；表现刷新交给 Visual。

你们的桥其实是三段

Bridge 子职责 常揉在一个 MB NineGrid
吃场景命中 / 指针 Bridge OnMouse / 按钮 GroundCardHitProxy 等 + PointerHitRouter
跨目录装配缝 Inspector UnityEvent 拖 Rules 静态 *Hook（如 AttackInputHook）
翻成架构意图 直接调 RulesModel 方法 AttackInputController → Submit*Command → Intake 
// HitProxy：只活在场景，注册到命中表
class GroundCardHitProxy : MonoBehaviour, IPointerHitTarget { ... }

// Hook：装配缝（非业务总线）
AttackInputHook.TrySubmitAttack = ...;

// Controller：翻成 Command
bool HandleMonsterSlotClicked(int slot) {
  return SendCommand(new SubmitAttackIntentCommand(slot));
}

GroundCardHitProxy.cs · AttackInputController.cs · 典型路径见 presentation.md ：Host / Hook → Controller → IntentIntake

一条攻击点击怎么过桥

玩家点怪物格
  → PointerHitRouter 命中 GroundCardHitProxy
  →（场地交战路径）AttackInputHook.TrySubmitAttack(slot)
  → AttackInputController.HandleMonsterSlotClicked
  → SubmitAttackIntentCommand
  → IntentIntake.Submit
  → Allow/Buffer 后进 Director / Core

对照作者： 点击 → UnitSelectionBridge → UnityEvent → RulesModel.Apply… 少了 Inspector 拖线，多了代码装配与结构护栏「不得绕过 Intake」。

UnityEvent 接线 vs 代码接线

Bridge + Inspector UnityEvent Hook + Controller + Command
谁看得见调用链 打开 Prefab/场景才完整 IDE 引用 + 结构测试可扫
改方法名 易静默断线 编译期失败（通常）
策划改接线 强（拖一拖） 弱（要改代码/装配）
多入口共用规则 都拖同一 Rules SO 都发 Command 进同一 Intake
作者总结已警告的坑，对你们同样成立： 调用链过长且藏在 Inspector 时，调试成本暴涨。 你们用代码接线换可追踪性；代价是「可视化拖拽装配」弱一截——这正是总图课说的取舍。

若用纯 Bridge+SO 重做攻击输入

  1. HitProxy 仍可留（或改回按钮/OnMouse，但你们有 ADR-0006 理由不回去）
  2. Bridge 上拖 AttackRequested Event Channel 或直连 RulesModel
  3. RulesModel / Core 门面资产执行合法性与写状态

能跑，但会削弱「IntentIntake 结构护栏」与程序集边界。 更现实的混用：配置/特效继续 SO；Bridge 层保持 Controller+Intake。
