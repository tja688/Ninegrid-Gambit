Rules Model：业务规则放哪，入口如何唯一

作者把「能不能做 / 做了改什么 / 取消怎么回滚」收进一个可拖的规则 SO。你们把规则真相放 Core，把意图门禁放 IntentIntake——同构的是「多入口共用一个中心」，不是「中心必须是 SO」。

作者的 Rules Model SO 在干什么

总结里的 Rules Model 更像 Application / Domain Service，而不只是存数据：

  • 判断：单位可选？技能可放？格子合法？
  • 应用：改 State / Field，Push 状态
  • 回滚：Cancel 时撤销业务影响（占位、路径、行动点……）
  • 不该：直接找 Camera、改 Canvas、播具体动画
为什么多个 Bridge 共用一个 RulesModel： 玩家、AI、教程、部署、回放都调同一套接口，避免「玩家一套规则、AI 复制一套」。 共用手段：大家都引用同一份 RulesModel.asset。

同一条「点一下想做事」

若把 Core 收成 Rules Model SO

理论上能：一个巨大 TableNineRulesModel.asset，Bridge 全拖它。

对你们这种体量，代价不对： 规则与表现程序集边界会被资产引用糊掉；EditMode 测 Core 不必起场景的优势变弱； 「拖错第二份 Rules」会比拖错 Field 更致命；和占格唯一归 Core、Batch-ack 等 ADR 更难护栏。 值得迁的是「多入口唯一收口」这一纪律——你们已经用 Intake 落地了。
SO 路线仍有的优点（小项目/强策划接线时）： 规则对象在 Project 可见、可热换不同 Rules 资产做模式变体、少写 GetSystem。 Hipple 也把「Systems in SO」当作可选柱子，不是唯一真理。 （Unite 2017）

优点 / 缺点（规则中心这一层）

Rules Model SO Core + Query + IntentIntake
唯一规则入口 靠共用一个资产 靠 Intake 护栏 + Core 写口
规则与表现边界 靠约定（Model 不碰 Camera） 靠程序集 + ADR + 结构测试
测试 可测 SO 方法；场景仍易缠进来 Core / Intake EditMode 成熟
AI/教程共用规则 Bridge 调同一 Model 同样应走 Command/Intake，禁止旁路改 Board
可视化装配 强 弱（代码装配）
