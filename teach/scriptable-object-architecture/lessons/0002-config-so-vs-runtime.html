Lesson 0002 · ScriptableObject 玩法

配置 SO：配方资产，不是运行时黑板

作者那套从「保存伤害、图标」讲起——这一块你们仓库里早就在用。先把它和 Field / Rules 剥开，后面才不会糊成一团。

先收紧上一课那句

「可拖拽装配」说对了操作面；更准的钉子是： 拖的是同一份资产引用。 对配置 SO，拖的是「用哪份配方」； 对 Field / Event，拖的才是「大家共用一块活数据 / 频道」。 本课只谈前者。

配置 SO 是什么

配置 SO 保存相对稳定、可被多处引用的配方：数值、图标、时序参数、策略入口。 它通常不回答「这一局玩家此刻选中了谁」。

作者怎么玩： AbilityDataSO 一类资产挂在按钮上——名字、伤害、距离、图标。 多个按钮可以引用不同配方；换数值改资产即可，不必改场景脚本。 （见你的总结「一、配置型 SO」。）
你们怎么玩（已经在玩）： CardEffectSO 及其实现（冲刺、闪白、序列）、 BattleEncounterProfileSO / Catalog、 CardFaceSlotRegistrySO、 各类 *VisualCatalogSO。 内容表（Luban / Catalog）管规则侧定义；这些 SO 多半管表现配方与视觉索引。

一个容易混淆点：带方法的配置仍是配置

CardEffectSO 有 PlayAsync——看起来像「逻辑对象」。 它仍是配置/策略资产：描述怎么播这段反馈，由编排层选用哪份资产。 它不是「当前正在播放的那一次」的共享状态容器；那次播放的上下文在 CardEffectPlayContext / 调用方手里。 

// 配方（资产）——可拖到装配槽
abstract class CardEffectSO : ScriptableObject {
  public abstract UniTask PlayAsync(CardEffectPlayContext context);
}

// 遭遇配方——击退、闪白策略、是否绑死亡回调
class BattleEncounterProfileSO : ScriptableObject { /* … */ }

源码： CardEffectSO.cs、 BattleEncounterProfileSO.cs。 Unity 官方基线： ScriptableObject。

作者若只用配置 SO，还缺什么

若整个项目停在配置 SO，仍然会出现：

  • 鼠标指示器要 Find 玩家才能读「当前技能」
  • UI / AI / 教程各自抄一套规则入口
  • 模块间靠单例或互相拖 MonoBehaviour 引用

所以作者继续往 Field、Event Channel、Rules Model 长——那些才是「松散 MVC」错觉的来源。 你们用 CompositionRoot + IntentIntake + Core 解决了同一批问题，配置 SO 只负责配方层。

若你们「用 SO 去组织」——配置层怎么做

其实保持现状即可：配方继续 SO，规则与会话状态不要塞进同一资产。

纯 SO 路线再扩 你们现况（推荐维持）
技能/特效参数 继续 Config SO 已有 Effect / Encounter / Catalog SO
当前选中 另做 Field SO 运行时上下文 / System，不升格为配置资产
合法性 Rules Model SO Core Query + IntentIntake
优点对照（仅配置层）： 两边相近——可复用、可在 Project 里改、多处引用同一配方、设计师友好。 你们还多了 Luban 内容管线与表现 SO 的分层，避免把规则数值和手感曲线揉进一个万能资产。
配置层陷阱： 给 Config SO 加「当前值」「监听列表」「战斗阶段」——它就滑成 Field/State，却仍顶着配置的名字。 下一课专门拆这条滑坡。
