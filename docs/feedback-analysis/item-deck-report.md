# 策划试玩反馈三方比对分析：道具卡相关条目

> 比对日期：2026-08-08
> 范围：仅探查，无任何文件改动。
> 三方来源：① 权威文档（`CONTEXT.md` / `docs/adr/` / `docs/code-map/`）；② 代码实施（`NineGrid.Core` / `NineGrid.Presentation` / `NineGrid.Content`）；③ 策划设计案（`Assets/Docs/九宫格登神/`）。

## 结论摘要

| 条目 | 判定类型 | 一句话结论 |
|------|----------|------------|
| 1. 固定道具卡不该随机爆出三张加入 | **设计冲突（策划新方向）＋ 一处可验证的体验缺陷** | 现状不存在「固定卡随机爆三张」——固定卡是**确定追加**入玩家侧卡组，但卡店固定流程与开局发牌均与策划预期不符：固定卡排在玩家侧卡组尾部，开局直摆三张**永远轮不到固定卡**；「开局随机三张」是设计案发牌机制原文规定的行为。策划建议的「三选一固定」为**新交互设计**，与 ADR-0022 及房间.md 现状条款冲突，需策划确认后立项。 |
| 2. 清关剩余道具卡未兑金直接移除 | **设计冲突（非 bug）** | 「清关残留不兑金、主动回收才 +10」是**三方完全一致**的权威设计（策划案原文、ADR-0025/0026、代码实现均如此）。反馈与既定设计直接冲突，属体验预期差异；玩家所指容器待确认，但道具卡格内容在代码路径中明确保留（跳过清理），不存在「已入手卡被移除」的实现路径。 |

## 条目 1：固定道具卡与「随机爆出三张」

**反馈原文**：固定道具卡不该随机爆出三张加入；爆出三张让玩家选一张固定可以。

### ① 设计案原文

- `01-核心概念/卡组.md`：玩家侧卡组每关开局从来源池**随机抽取常规道具卡**直到达到容量；「关卡结束后，将玩家侧卡组和九宫格上残余道具卡全部移除（不兑金；主动回收才 +10 金币）」。
- `02-机制/发牌机制.md`（发牌规则）：**「从玩家侧卡组中抽 3 张卡，随机摆放在空格子上」**——开局三张是策划案明文规则，且明确「随机摆放」。
- `01-核心概念/房间.md`：**「道具卡固定：花费 50 金币，本局永久。此后每次玩家侧卡组生成时，固定包含一张选定的道具卡」**——策划案现状条款是「固定卡静默包含」，**无三选一**。
- 特殊房（同文件）：宝箱奖励房 = 1 宝箱卡 + **3 张随机道具卡**；道具奖励房 = 2 属性卡 + **3 张随机道具卡**——「随机三张」的另一个出处是奖励房货架。

### ② 权威决策（ADR / CONTEXT）

- **ADR-0022（节点装填模型）**：玩家侧卡组 = 按**容量**从**来源池**随机生成 → 叠加**固定卡列表** → 叠加房间注入卡；每战斗节点开局重生成，关卡结束发牌侧全清。固定卡列表跨节点持久（卡店「道具卡固定」服务写入）。
- **ADR-0033（稀有度投放控制）**：随机来源池只含常规 White（12 张）；特殊卡只走定向渠道。
- **ADR-0025（道具卡格持续持有）**：卡店/奖励产出直写道具卡格；「道具卡固定」写入 `PlayerModel.FixedItemCardDefIds`，与道具卡格是两个容器。
- **CONTEXT 玩家侧卡组**：与道具卡格是两个容器；固定卡属玩家侧卡组生成规则的一部分。
- **ADR-0031（属性房三选二）**：**已有「进房生成 3 个加权候选 → 玩家选 2」的会话先例**——引擎内三候选会话通道（`PendingChoiceModel` + `RewardItemChoice` 相位 + `SelectReward`）现成可用，若策划确认「三选一固定」可复用此通道。

### ③ 代码实施路径

- 玩家侧卡组生成：`RewardSystem.AddRunPlayerSideCards`（`NineGrid.Foundation/NineGrid.Core/Systems/RewardSystem.cs:560-586`）——① 按 `ItemDeckCapacity`（默认 6）从来源池有放回随机抽；② **直接追加固定卡**（`:577-582`，`player.FixedItemCardDefIds`）；③ 追加房间注入卡。
- 固定卡写入：卡店「道具卡固定」二级选择——`PhaseSystem.SelectTavernFixItemConfirm`（`PhaseSystem.cs:1112-1139`）从**来源池列表**（`BuildTavernFixItemCandidates` `:1156-1174`，非三张候选、非三选一）点选一张 → `PlayerModel.AddFixedItemCard`（`PlayerModel.cs:235-244`）。
- 开局「爆三张」：`OpeningDealAction.PlacePlayerCardsDirectly`（`BoardDeckActions.cs:204,233-271`）从 `PlayerCardPool` **取前 3 张**（`NodeDeckOptions.PlayerOpeningCount = 3`，`RewardSystem.cs:312`）随机摆位；剩余洗入战斗卡组（`:217` `DrainStagingPool`）。
- **可验证的体验缺陷**：生成顺序为「随机容量 N → 固定卡 → 注入」（`RewardSystem.cs:566-585`），`PlacePlayerCardsDirectly` 只取 pool **前 3 张**——只要随机张数 ≥3，**固定卡必被压在开局直摆三张之外**，只能进抽牌堆等补牌。玩家固定了一张卡后，每关开局看到的仍是三张纯随机卡，固定卡大概率中后期才补上来。这正是「固定道具卡=随机爆出三张」观感的代码根源：**固定机制存在，但玩家在开局三张里感知不到它**。契约测试佐证顺序（`PlayerSideDeckRegenContractTests.cs:78-79`「容量2 + 固定1」；`RoomOpeningInjectContractTests.cs:147-148` 固定卡排 [1]、注入排 [2]）。
- 已存在的三候选会话先例：属性房三选二（`RewardSystem.BuildAttributeCandidates` `:683-720` + `OfferAttributePickSessionAction`）；遗物三选一（`RememberUnselectedRelics`）。

### 判定

**设计冲突（策划新方向）＋ 一处可验证的体验缺陷。**

1. 「固定卡随机爆出三张加入」在实现上不成立：固定卡是**确定追加**，不是随机；玩家看到的「随机三张」是发牌机制.md 明文规定的开局三张（随机生成 + 随机摆位），与固定机制无关，但二者在玩家体验里被混淆。
2. 策划建议「爆出三张让玩家选一张固定」是**新交互设计**，与设计案现状条款（房间.md「固定包含一张」）及 ADR-0022（固定卡静默叠加入）冲突——不是修 bug，需要策划/产品确认新方向，再决定是否立项（可复用属性房三选二会话通道，工作量可控）。
3. 无论新方向与否，**「固定卡排在开局三张之外」是可复现的实现细节**：若固定卡意图是「每关稳定可用」，现状只保证「进卡组」不保证「开局上场」，与玩家对「固定」的预期存在落差，建议单独确认（改直摆顺序 / 固定卡开局直摆优先 / 或按新方向做三选一会话）。

涉及 ADR：ADR-0022（玩家侧重生成 + 固定卡追加）、ADR-0033（来源池常规限制）、ADR-0025（固定卡列表与道具卡格分离）、ADR-0031（三候选会话先例）。

## 条目 2：清关时剩余道具卡直接移除、未兑金

**反馈原文**：关卡结束时，剩余道具卡未转化为金币，直接移除了什么都没加。

### ① 设计案原文（策划案自身即「不兑金」）

- `01-核心概念/卡组.md`：「关卡结束后，将玩家侧卡组和九宫格上残余道具卡**全部移除（不兑金；主动回收才 +10 金币）**」。
- `01-核心概念/经济.md`：「主动回收（拖入回收区确认）道具卡：**每张 +10 金币（清关残留不自动兑金）**」。
- `01-核心概念/道具卡格.md`：仅定义「存放已拾取道具卡的区域，初始 3 格」——无清关兑金条款。

→ 策划案从未规定「清关自动兑金」；**反馈与策划案原文直接冲突**。

### ② 权威决策（ADR / CONTEXT）

- **ADR-0025（道具卡格持续持有）**：「清关不再把格内卡兑金清空」「场上未入手残留的处理见 ADR-0026」；回收 = 主动拖入回收区，每张固定 +10 金。
- **ADR-0026（离开机关唯一清关）**：清关收场「那一拍清掉场上残留（未拾取道具 / 剩余怪 / 其它机关）且**不兑金**；道具卡格内容按 ADR-0025 保留」；「击破前玩家可一直留在场地交互（拣选、回收、击杀赚钱）——不是另开拣选相位」。
- **ADR-0022**：关卡结束时玩家侧卡组（发牌侧）**全清**（每关重生成模型的一部分），不清不兑。
- **CONTEXT「清关」**：「场上残留（未拾取道具 / 剩余怪 / 其它机关）一并清场且不兑金；道具卡格内容保留」；**「清关拍自动兑金」被列为明令 Avoid**。

### ③ 代码实施路径（与设计一致）

- 清关入口：`PhaseSystem.CompleteNodeIfCleared`（`PhaseSystem.cs:1847-1872`）——击破离开机关后：
  - `IEconomySystem.SettleUnusedHelpCards()`（`:1867`）→ `EconomySystem.RemoveLingeringHelpCards`（`EconomySystem.cs:224-252`）：收集**抽牌堆（DrawPile）＋玩家侧发牌池（PlayerCardPool）＋场上**的 HelpCard 移除，`cause=settleRemove`；**注释明确「道具卡格由 RemoveLingeringHelpCards 跳过」**（`:234`）；返回值恒 0（`:91-96` 不兑金）。
  - `IEconomySystem.ClearResidualTraps()`（`:1868`）→ `EconomySystem.cs:98-137`：清场上残留怪/机关，`cause=clearResidualBoard`；`ReactToRemovedCards`（`:153-209`）对 `clearResidualBoard / clearResidualTrap` 明确**跳过击杀赏金**（`:177-181`）。
- 道具卡格保留：`DeckModel.ItemSlotUids`（`ZoneId.ItemSlots`）不在上述任何清理集合内；表现层跨节点经 `BattleSessionExecutor.CaptureRunInventory/RestoreRunInventory`（`BattleSessionExecutor.cs:333-479`）显式保存并恢复 `ItemSlotDefIds`。
- 主动回收兑金路径（未受影响）：`AwardRecycleItemSlot`（`EconomySystem.cs:80-89`，`RecycleItemSlotGold`=10）。
- 契约测试锁定该语义：`LeaveTrapClearContractTests`（缝注释「收场清残留不兑金」）、`PlayerSideDeckRegenContractTests`（清关保留道具卡格）。

### 判定

**设计冲突（非 bug）。** 三方（策划案原文 / ADR / 代码）对「清关残留不兑金、主动回收 +10」**完全一致**；本反馈与之直接冲突，是试玩体验预期（习惯性期待「关卡结算自动兑换」）与已落地明确设计（恋战经济：清关前自由拣选/回收/击杀，击破那一拍才扫场）之间的差异，而非实现缺陷。

需与策划确认的两个子问题（本报告不断言）：

1. **玩家所指「剩余道具卡」是哪个容器**：
   - 场上 / 发牌侧残留（本关随机生成的卡）→ 现状移除不兑金，**符合设计**；
   - 道具卡格（已入手 / 已购入卡）→ 代码路径**不会**移除它（清关保留），若玩家观察到被移除属 bug 线索，需复现证据（回放 / 截图 / 节点号）；
   - 玩家侧卡组与道具卡格是两个容器（CONTEXT / ADR-0022 / ADR-0025 强调），反馈条目很可能混用了二者。
2. **是否要推翻「清关不兑金」**：若策划改主意要「清关自动结算兑金」，将连带修改 ADR-0025 / 0026、CONTEXT「清关」词条、`EconomySystem` 两个收场路径与相关契约测试——属 Spec 级决策，不是顺手改动。

涉及 ADR：ADR-0021（原清关兑金条款已被 0025/0026 取代）、ADR-0025、ADR-0026、ADR-0022。
