# 效果责任自陈：拆除外部场域门禁

## 决策

效果的适用边界由**效果自己声明**，不由外部按场域拦截：

1. **效果自陈责任。** 每条效果显式声明它适用的场景、对象与条件。享有多大权利（产生多大影响），就承担多大责任（声明多严的适用范围）。
2. **拆除外部风控。** `EffectOwnerScopeGate`（怪物技能/帮助卡默认只响应本卡相关批次）与区域门禁 `IsCardOwnedEffectInTriggerableZone`（卡组/坟场/移除区不触发）退休。它们表达的容器物理差异，改由效果在自陈中表达。
3. **同一效果不得因上下文呈现两种形态。** `ownerOnly`、`excludeSelf`、`actorIs`、`targetIs`、`targetNot`、`sourcePrefix`、`excludeCause` 这类上下文开关参数取消，拆成语义唯一的独立原子（如 `OnUseHelpCard{ownerOnly}` → `OnSelfUsed` / `OnAnyHelpCardUsed`）。原子名即语义，不依赖默认值。
4. **自陈分两块。** `requires` 声明「我适用于什么场景」（需场上实体 / 需被使用 / 需处于某区域），`conditions` 声明「此刻的玩法条件」（血量、格位、计数）。两者诊断级别不同：`requires` 不成立属装配错误，`conditions` 不成立属正常玩法。
5. **新建未触发探查能力。** 能回答「这条效果为什么没响」，并区分上述两类原因。

## 为什么

改版前效果与卡一一绑定（150 条效果复用数为 0，见 [ADR-0009](0009-parameterized-effect-templates.md)），外部门禁按容器裁决是安全的——每条效果都是为那张卡手写的。一旦效果变成可跨容器装配的模板，门禁就会造成最坏的失败模式：**装配"成功"、DSL 校验通过、运行时静默什么都不做**。

例：模板「当任意帮助卡被使用时获得 N 金币」装到遗物上完美工作；装到帮助卡上时，那张卡待在手牌里，被区域门禁拦掉，不报错、不崩溃、就是不生效。你会以为是数值没调好。

现有四道护栏性质不同：`typeTag`（`【类型遗物】`）与 `verb` 约束是纯字符串校验、人为规定，可直接拆（在 ADR-0009 中取消）；`EffectOwnerScopeGate` 与区域门禁表达的是**真实物理差异**——遗物没有场上实体（`ownerUid=0`），帮助卡与怪物有卡实体且会在手牌/场上/坟场间移动。这条差异拆不掉，但**应由效果自陈而非外部拦截来表达**：外部拦截把边界藏在容器概念里，自陈把边界写在效果自己身上，装错了能被看见。

现有 DSL 词汇（`CardZone`、`EventFilter`、`AtSlot`）已足够表达适用场景，不需要发明新概念。

## 考虑过的替代

- **保留门禁、模板额外声明 `usableBy` 白名单**：否决——白名单靠人维护，且把同一件事表达两遍（模板说能装哪、门禁又拦一遍），两处不一致时以谁为准无解。
- **从触发原子自动推导可装容器**：否决——`OnBattle` 对遗物（全局监听）与怪物技能（限自身）都成立，推导不出唯一答案；靠 `ownerOnly` 参数补足又违反「单形态」。
- **完全自由、不做任何声明，运行时注册失败打 Error**：否决——注册成功但条件永不满足的情况打不出 Error，仍是静默失效。
- **给遗物造虚拟实体/常驻区域，让三种容器物理同构**：否决——为消除差异而虚构实体会污染 Core 模型，且「遗物在坟场」这类问题没有自然答案。
- **`requires` 与 `conditions` 合并为一块**：否决——探查手段将无法区分「设计如此的不触发」与「装错了的不触发」，日志里会是一堆无法分诊的 `condition=false`。

## 后果

- **风险方向反转，且面很大。** 卡挂载效果（HelpCard 33 + MonsterSkill 74）共 107 条，其中 **78 条没有任何显式场景声明**（`CardZone` 仅 5 条、`EventFilter` 21 条、`AtSlot` 10 条），完全靠隐式门禁兜着。例：`help.fireball.use` 的 DSL 只说「触发：帮助卡被使用 / 目标：选中怪物 / 造成伤害」，「只在我自己被使用时」那句是门禁与 `ownerOnly` 默认值替它说的。门禁拆掉而声明没补，失败模式从「静默不触发」翻转为「乱触发」——用一张药水，手牌里的火球炸弹破击锤全放一遍；一只怪物死亡，场上所有亡语一起响。乱触发会污染整局状态，且症状看起来像别的系统坏了。
- **因此强制实施顺序：先补声明，后拆门禁。** 门禁在场时补声明只会更严格，最坏症状是「该触发的没触发」，能被 EditMode 与试玩发现；78 条全部补完、测试全绿后再摘门禁，那一步是行为等价的。顺序反过来会有一段时间游戏不可玩。
- 31 处上下文开关参数对应的原子需拆分并重新校验 `EffectAtomSchemas`。
- 未触发探查是新建能力：ADR-0003 的诊断关联层（ChainId / ChoreoSeqId）记的是「发生了什么」，不记「为什么没发生」。
- `EffectAtomSchemas.ValidateCardOwnedTriggerScope`（怪物技能 `OnBattle` 须带 `EventFilter`/`AtSlot` 等）从「外部强制」改写为自陈校验。
