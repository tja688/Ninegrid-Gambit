# 行动计数统一为倒计时语义，开火窗口一次性

## 决策

1. **「每 N 次」统一为倒计时语义。** 计数器存的是「还差几次」：置为 N，相应行为每发生一次 −1，减到 0 即触发并重置为 N。取代现有的两套数学。
2. **开火窗口是一次性的。** 倒计时归零的那一拍就是窗口；若开火资格不通过（位置条件不满足 / 被禁止行动），**取消本次行动并把倒计时重置为 N**，不保留蓄力、不停在 0 等下一拍。
3. **攻击模式与效果各用独立命名的计数器。** 攻击模式用保留 key；DSL 效果沿用 `CoreCounterKeys.EffectCounterPrefix + instanceId + …`。共享的是计数设施（`CardInstance.Counters`）与语义，**不是同一个计数值**。
4. **`OnInteract` 补 `every` 参数**，使技能可以复用互动计数。
5. **`OnSelfMove` 的 `every` 从「累计 % N == 0」迁移为倒计时**；`OnCumulative` 的按量累计表达为「倒计时减去 delta，≤ 0 则触发并加回 N」。
6. **倒计时可被效果加减速**；攻击模式本身不可被改写（[ADR-0011](0011-monster-attack-pattern-intrinsic.md)）。

## 为什么

**一套数学同时解决三件事。**

- **卡面直读。** 卡面「行动计数」槽显示的就是倒计时本身，不需要「阈值减累计」的换算，卡面也不需要知道阈值是多少。
- **可被效果加减速而不错位。** 「使目标怪的行动计数 +1」在倒计时下是自然的加法；在模运算下修改计数值会让该效果的**相位永久偏移**——它不是延后一次，而是从此以后每次都错开。
- **三套收敛成一套。** 现状是 `OnSelfMove` 用模运算（只增不减、永不清零）、`OnCumulative` 用阈值减、`OnInteract` 根本没有 `every`（技能想复用互动计数写不出来）。同一个「每 N 次」概念有三种行为。

**窗口模型是唯一让攻击模式梯度自洽的选择。** 玩家默认在中心格 5，正交是 2/4/6/8、对角是 1/3/7/9；顺时针旋转路径 `1→2→3→6→9→8→7→4→1` 上，正交与对角**严格交替**。以「每次互动都旋转」为一阶近似估算期望出手间隔：

| 模式 | 位置条件 | 阈值 | 窗口模型 | 蓄力模型 |
|------|----------|------|----------|----------|
| 普通近战 | 正交 | 3 | 6 拍 | 3.5 拍 |
| 斜角近战 | 对角 | 3 | 6 拍 | 3.5 拍 |
| 全向近战 | 八向 | 3 | 3 拍 | 3 拍 |
| 普通远程 | 无条件 | 5 | 5 拍 | 5 拍 |

窗口模型下梯度干净：**全向 > 远程 > 单向近战**，正好对应「位置限制越松、频率越慢」的设计意图。蓄力模型下由于正交/对角严格交替，蓄满后平均只需再等半拍就能进入射程，于是**远程变成全场最弱**（5 拍）——比带位置限制的近战（3.5 拍）还差，梯度直接倒挂，`普通远程` 与 `全向近战` 的区分也随之失去意义。

**关于「错过窗口是否浪费了时间」**：玩家确实可以通过控制旋转（砍不死就不旋转）压制某只怪的窗口，但这不是免费的——砍不死的怪每拍都会回击。玩家是用血量买压制，时间被兑换到了别处（详见 [ADR-0012](0012-enemy-action-phase-volley.md)）。

**关于「为什么不共用同一个计数值」**：一只怪同时有攻击模式（阈值 3）和一条「每互动 2 次」技能时，共用计数会让两者互相偷计数，且谁重置谁的语义无解。

## 考虑过的替代

- **蓄力模型（打不着就保持满蓄，一旦位置合适立即开火）**：否决——见上梯度倒挂。它更「直觉」，但会让位置条件退化为「延迟半拍」，四个模式几乎只剩阈值差异。
- **错过窗口时倒计时重置为 1（下一拍再试）**：否决——介于窗口与蓄力之间，漏洞与梯度都变浑：普通近战期望约 4 拍，与远程的 5 拍拉不开距离，而「错过有代价」这层含义又弱到玩家感受不到。
- **统一为累计语义（沿用 `OnCumulative` 的阈值减）**：否决——卡面显示需要 `阈值 − 累计` 的换算，卡面因此要知道阈值，与「卡面只消费已提交的可见值」相冲突（[ADR-0005](0005-card-face-beat-commit.md)）。
- **统一为模运算**：否决——无法支持效果加减速而不错位相位。
- **最小改动：攻击模式自用倒计时，DSL 侧只给 `OnInteract` 补 `every`**：否决——长期三套语义共存，「每 N 次」在文档里是一个词、在代码里是三种行为，是内容作者踩坑的稳定来源。
- **攻击模式与效果共用同一个计数值**：否决——见上。

## 后果

- **现有 `every` 内容行为等价但需回归。** 受影响的是 `OnSelfMove` 系模板：`tpl.skill.flame_breath.move`（每移动 4 次）、`tpl.skill.stroll.move`（每移动 1 次）、`tpl.skill.strong_combo.move`（每移动 1 次）等。无外部干预时倒计时与模运算完全等价（第 N、2N、3N… 次触发），`every: 1` 亦等价（每次都触发），但迁移必须由 EditMode 覆盖。
- **`OnCumulative` 的 `counterKey` 存储含义反转**（从「已累计量」变成「剩余量」），跨存档兼容性需确认。
- **`CoreCounterKeys` 需要一个攻击模式专用的保留前缀**，并与 `EffectCounterPrefix` 明确隔离。
- **倒计时上卡面必须走结算指令链路**，不能在 View 上自己减（见 ADR-0012 后果）。
- **「每战斗 N 次」的被数对象取决于 `OnBattle` 是否收紧为交战作用域**，该项在 ADR-0012 中标记为暂定、未定案。
- **一阶估算的前提是「每次互动都旋转」。** 实际上未击杀的战斗不旋转，因此上表是长期期望而非逐局保证；平衡调参时应以实测为准。
