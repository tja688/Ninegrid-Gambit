# 效果参数化模板与跨容器装配

## 决策

效果从「卡专属的具名一次性实例」改为「**参数化模板 + 装配引用**」：

1. **效果模板与具体卡脱钩。** 模板描述一类效果诉求（如「对选中目标造成伤害」），不绑定任何一张卡，可被帮助卡、遗物、怪物技能共同引用。
2. **参数写在装配引用上。** 卡文件里的一条装配引用同时给出模板 id 与实参（`amount` 等）。一张卡的全部信息在一个文件里看得全；全局平衡靠脚本批量改，不引入数值间接层。
3. **`typeTag` 与 `verb` 这两道纯字符串校验取消。** 模板可装到哪些容器由 [ADR-0010](0010-self-declared-effect-responsibility.md) 的效果责任自陈裁决，不由容器名匹配。
4. **描述随模板走，分两级产出。** 详情描述 = 人手写的卡级概括 + 从装配结果自动展开的词条解释；卡面基础描述（检查描述）人手写，插 `{装配id.键}` 由装配实参填初始配置值（不随战中剩余跳变）。战中/实例体感句与倒计时剩余改由**局内描述投影**承担——见 [ADR-0035](0035-dual-description-projection-and-assembly-param-refs.md)。
5. **词条是项目级共享语汇。** 约百条量级、玩家可读、单一认知分区 + `Others` 兜底；一个词条可被多个模板引用，解释只写一遍。载体是现有 `[Poison]` 方括号机制的升格——从「代号 → 图标」扩为「代号 → 图标 + 名称 + 解释」，卡面渲染图标、详情页展开解释，同一份数据两种展开。
6. **分类落为三条正交轴**：`deckId`（卡组，决定卡背；怪物那边兼任遭遇编排单位）、`role`（功能角色粗轴，攻/防/功能，接投放均衡）、`tags`（细轴多值）。连同已有的 `rarity`，全部代号主键、中文只做显示名。  
   **消歧**：`role` 的「防御」（`ContentRole.Defense`）只回答「这张卡在 build 投放里偏防向」，**不是**战斗属性，也不等于护甲 / 伤害减免。战斗减伤与护甲语义见 [ADR-0028](0028-damage-formula-armor-and-reduction.md)。

## 为什么

效果引擎从第一天起就支持共享——id 引用、全局原子注册表（75 个原子）、一卡可挂多效果。但**实际复用率是零**：150 条效果里被 2 个及以上容器引用的有 **0 条**，149 条各被恰好 1 个容器引用，1 条孤儿。原因是每条效果都按卡命名的一次性实例（`help.fireball.use`、`skill.beggar_bond`），逻辑相同也要重写一条。所谓「装配」在这种形态下只是换个 id 引用，本质没变。

描述之所以分两级手法：卡面描述是**卡级概括**（一句话说清整张卡），一张卡挂 3 个效果时机器拼不出概括，只能人写；详情描述是**效果级逐条**，参数插值后与实际逻辑永不脱节。词条走同一套方括号码，保证「卡面提到什么、详情就一定解释什么」，不可能脱节。

分类之所以要粗细两轴：现有 27 张帮助卡被分进 8 个中文 tag（直伤 7、防向 5、恢复 3、位移 3、经济 3 等），平均一桶 3.4 张。这个粒度撑不起「一次给 3 张卡、至少有一张攻击向」这类均衡规则——规则会写成一长串 tag 枚举，加卡就要改规则。均衡需要 3–4 个稳定的粗桶，检索与百科需要可增长的细标签。粗桶里的「防御」仅作投放角色名，勿与战斗「护甲」混读。

分类的真正消费方是奖池：现在 9 个池共 **156 条手工白名单**，每条硬写一个 `def_id` + `weight`，加一张卡要往 4 个池各贴一遍，且没有任何池按条件筛选。有了 `role` 与 `rarity` 轴之后，156 条条目可塌缩成 9 条查询规则。没有消费方的分类字段是死数据。

## 考虑过的替代

- **保持具名实例、只去掉容器限制**：否决——不解决复用率为 0 的根因，仍是一效果一条目。
- **效果 DSL 内联到卡文件、取消效果表**：否决——复用退化为复制粘贴，平衡改动要逐卡扫。
- **参数存独立数值表、卡只引用条目 id**：否决——全局平衡略便利，但看一张卡要跳两个文件，与「一卡一文件看得全」冲突；全局平衡用脚本批改同样能做。
- **模板带默认值、卡只写偏离值**：否决——卡面上看不出实际数值，读卡文件不再自明。
- **词条一模板一条 / 一原子一条**：否决——75 个 DSL 原子是程序语言不是玩家语言；模板名 1:1 会让「护甲」这类共享机制的解释重复 N 遍。
- **单轴统一分类（`group` 字段按卡种解释语义）**：否决——怪物的卡组与帮助卡的功能角色除了名字没有共同消费逻辑，混轴会让投放器和卡背两个消费方互相打架。

## 后果

- 150 条效果需迁移为「模板 + 装配引用」，迁移中会暴露哪些逻辑本可共用。
- 效果定义上的 `containerType` 语义改变：不再是运行时准入限制，仅作分类/检索信息。编辑器 IA 仍按卡种默认只展示/多载同类模板（道具/遗物/怪物技能）；JSON 模板池保持同构，不因此拆三套 schema。
- `CardFaceDescriptionIconCatalog` 升格为词条表，名称与 `CONTEXT.md` 中「描述图标引用」条目须同步修订。
- 奖池从白名单改查询规则，`RewardPool` / `RewardEntry` 数据结构变更。
- 卡组新增视觉消费方（卡背），`CardPresentationConfigDto.deckId` 从「怪物填、其余空串」补齐为全卡种必填。
- 稀有度 → 卡框颜色目前算得出但未接线（`StandardCardView.SetFrameColor` 全仓库零调用方），随本决策一并接通。
